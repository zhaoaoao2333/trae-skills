# 项目管理规则

## 项目资产

### 项目ID
- 格式：P + 三位数字（如 P001、P002）
- 由注册表分配，不重复不回收

### 文件夹命名
- 格式：P编号-项目简称-年月（如 P001-电商APP-2606）

### 标准子目录
```
P编号-项目简称-年月/
├── 00-项目记录/       ← 确认记录、断点续传、上下文记忆、版本记录
│   ├── context-memory.md   ← 上下文记忆文件
│   ├── version-log.md      ← 版本记录文件
│   ├── 会议纪要/
│   └── 决策记录/
├── 01-需求文档/       ← 当前最新版PRD + 历史版本归档
│   ├── PRD.md              ← 最新版（小改直接覆盖）
│   └── 版本记录/           ← 仅大改动时存档
├── 02-过程文件/       ← 中间产物、参考材料（项目结束可清理）
│   ├── 需求梳理/
│   ├── 参考材料/
│   └── 草稿/
├── 03-思维导图/       ← 导图文件，直接放根下，不分类型子文件夹
│   ├── 功能清单_v1.2.mm    ← 最新版
│   ├── 业务流程_v1.0.mm
│   └── 历史版本/           ← 旧版本归档
├── 04-原型/           ← 当前最新版原型 + 历史版本
│   ├── index.html          ← 最新版（小改直接覆盖）
│   ├── 原型截图/           ← 仅首轮/重大修改/交付前更新
│   └── 版本记录/           ← 仅大改动时存档
├── 05-交付物/         ← 最终对外交付（按批次/日期分文件夹）
├── 06-技能包/         ← 本项目关联的技能包快照
│   └── 原型产出skill/
│       └── v{版本}_{日期}/ ← 每次技能包更新后存快照
└── 07-设计资产/       ← 设计素材（按需创建，没有就不建）
    ├── 截图/
    ├── 图标/
    └── 素材/
```

### 各目录更新时机

| 目录 | 创建时机 | 更新时机 | 备注 |
|------|---------|---------|------|
| `00-项目记录/` | 项目启动时 | 里程碑/会议/决策后 | 轻量文本，消耗低 |
| `01-需求文档/` | 进入阶段五 | PRD 定稿/重大修改时 | 小改直接覆盖，不改版本记录 |
| `02-过程文件/` | 阶段二~四 | 过程中按需 | 项目结束后可清理，不长期保留 |
| `03-思维导图/` | PM要求或AI建议时 | 导图内容变更时 | 一张导图通常只迭代1-2次 |
| `04-原型/` | 进入阶段六 | 原型定稿/重大修改时 | 小改直接覆盖html |
| `04-原型/原型截图/` | 首轮生成/交付前 | 重大修改后/交付前 | 非每次修改都截图 |
| `05-交付物/` | 交付时 | 每批次交付时 | 按需创建 |
| `06-技能包/` | 项目启动时 | 技能包更新后 | 只存快照，不频繁操作 |
| `07-设计资产/` | 需要时 | 按需 | 没有就不建 |

**Token节省原则**：
- 小改动直接覆盖原文件，不生成新版本
- 版本记录只在"结构/模块/流程级改动"时创建，文案/样式/bug修复级改动不触发
- `02-过程文件/` 是临时目录，项目收尾时清空或归档，不累积
- 截图用压缩格式，不保留中间过程的截图

### 项目注册表
- 位置：团队共享根目录
- 按状态分表管理

## 项目初始化

新项目必须先创建文件夹和标准子目录，按规范命名。

## 注册表管理

注册表为唯一真实来源，每次里程碑自动更新状态。

## 上下文管理

- 切换项目必须重置上下文
- 检测到异议主动提醒
- 每次确认写记录到 `00-项目记录/`，上下文断了可无缝恢复

## 上下文记忆管理

### 记忆文件维护

- **位置**：`00-项目记录/context-memory.md`
- **维护者**：AI 自动维护，PM 可查看
- **更新时机**：每个阶段结束时自动追加
- **读取时机**：每个阶段开始时自动读取

### 记忆内容规范

每条记忆记录包含：
- 日期时间
- 阶段名称
- 要点摘要（一句话）
- 详细内容（如有需要）
- 置信度标注（确定/推测/待验证）

### 遗忘检查

生成产出物前，AI 必须：
1. 读取记忆文件
2. 对照检查产出物是否包含所有已确认要点
3. 发现遗漏立即修正
4. 记录修正原因到记忆文件

## 版本回溯管理

### 版本记录维护

- **位置**：`00-项目记录/version-log.md`
- **维护者**：AI 自动维护
- **更新时机**：每次产出物保存时记录

### 版本命名规则

| 改动级别 | 判断标准 | 版本变化 |
|---------|---------|---------|
| **大改动** | 结构重组、新增模块、流程变更、页面层级调整 | v1.0 → **v2.0** |
| **中改动** | 功能调整、页面增删、规则变更、交互变更 | v1.0 → **v1.5** |
| **小改动** | 文案修改、bug修复、样式微调、细节优化 | 不改版本号，直接覆盖 |

**文件命名格式**：`{文件名}_v{版本号}_{YYYYMMDD}.{后缀}`

**版本记录触发原则**：
- 大改动和中改动 → 存档旧版本到 `版本记录/` 目录，生成新版本号
- 小改动 → 直接覆盖原文件，不生成新版本

### 文件版本保存

- 每个阶段产出物保存为独立文件
- 文件名格式：`[内容]-v[版本号].md`
- 示例：`流程梳理-v1.0.md`、`PRD-v2.0.md`、`原型-v3.0.html`

### 回溯操作规范

1. PM 提出回溯请求（「回溯到 v1.2」）
2. AI 读取版本记录，定位目标版本
3. AI 加载目标版本的产出物
4. AI 确认回溯内容（展示关键差异）
5. PM 确认后，从目标版本继续工作
6. 新版本号接续（回溯到 v1.2 → 新版本 v1.3）
7. 记录回溯操作到版本日志

## 产物修改回溯规则

> **核心原则**：只改结果不改规则 = 治标不治本。每次修改必须回答"这个问题的根因是什么"和"还有哪里用了同样的逻辑"。

### 修改流程

收到修改反馈时，按以下流程执行：

```
发现问题
  ↓
定位问题来源（PRD描述 / 设计纲要决策 / 代码实现）
  ↓
如果是PRD/设计纲要层面的问题
  → 修改PRD或设计纲要
  → 检索同类问题（其他页面是否有相同根源）
  → 一并修改所有受影响页面
  → 更新版本记录
  ↓
如果是纯代码实现层面的问题
  → 直接修改原型代码
  → 检查其他页面是否有同类实现问题
  → 如有，一并修改
```

### 三问必答

每次修改前，AI 必须回答以下三个问题：

1. **根因是什么** — 这个问题的源头在PRD、设计纲要、还是代码实现？
2. **还有哪里受影响** — 其他页面/模块是否使用了同样的逻辑或设计决策？
3. **需要改哪些文件** — 列出所有需要修改的文件清单，一次性修改

### 禁止行为

- ❌ 只改报错的地方，不追溯根因
- ❌ 改了代码但PRD/设计纲要中对应描述未同步更新
- ❌ 同类问题只改一处，其他地方留着不管
- ❌ 不记录修改原因和影响范围

## 防幻觉规则

| 置信度 | 处理方式 |
|--------|---------|
| 确定 | 直接陈述 |
| 推测 | 标注「待验证」 |
| 未知 | 直接说不知道 |

禁止：
- 编造竞品功能
- 技术断言
- 行业数据
- 不存在的案例

## 项目实战经验（从实际项目沉淀）

> 以下经验来自P001-高速服务区物业等项目的实战经验，是流程规范和设计规范的重要补充。

### 流程经验

1. **Skill加载不可缺失**
   - 项目初始化时必须确认skill已正确加载
   - 如skill未加载或加载错误，产出将严重偏离预期
   - 每次新项目启动时，先检查skill状态

2. **设计纲要不可跳过**
   - 即使PM催促，也必须先输出并确认设计纲要
   - 跳过设计纲要的直接后果：原型方向错误、反复修改
   - 设计纲要是"把设计想清楚"的关键步骤

3. **分阶段边界清晰**
   - 文档阶段（PRD）和原型阶段必须有明确的PM确认节点
   - 不可在PRD未确认时开始原型生成
   - 每个阶段结束必须获得PM确认信号

### 技术经验

1. **SPA导航是Bug高发区**
   - tab-bar显隐、pageStack管理、返回逻辑是原型中最容易出问题的部分
   - 必须建立SPA导航自检清单（8项检查），每次生成后强制执行
   - 常见问题：二级页面未隐藏tab-bar、返回后未显示tab-bar、多page同时active

2. **home-indicator常被忽略**
   - iPhone X及以上机型的home-indicator会遮挡底部导航
   - 需在容器约束规范中明确适配要求
   - 检查方法：在iPhone X模拟器中验证

3. **UI一致性需要铁律**
   - 卡片化、间距、字号必须在设计纲要中显式声明
   - 不同端口（如员工端vs管理端）必须用不同的设计参数
   - 避免用一套设计参数覆盖所有端口

### 迭代经验

1. **v1.0往往不符合预期**
   - 初次生成后必须经过审查→修复→再审查
   - 设计师审查能发现PM遗漏的问题
   - 不要期望一次生成就完美

2. **重新设计有时比修复更快**
   - 当v1.0偏离严重时，重新设计可能更高效
   - P001项目中员工端从v1.0到v3.0的重新设计带来了质的提升
   - 判断标准：修复成本 > 重新设计成本时，选择重新设计

3. **用户群体差异决定设计分化**
   - 同一业务系统的不同端口，因使用者能力不同，应采用不同设计语言
   - 低操作能力用户：极简大字号、单路径、强引导
   - 效率型用户：数据看板、快捷入口、批量操作
   - 设计分化应在设计纲要阶段明确

### P005项目实战经验（布局层与代码层）

1. **CSS定位差异必须区分清楚**
   - `absolute`定位元素不受父元素padding影响，`relative`定位元素受影响
   - 这是导致状态栏和navbar重叠的根本原因
   - 规范中必须明确定义每种定位的使用场景和偏移补偿

2. **动态方案必须覆盖所有入口**
   - 颜色切换、状态更新等动态逻辑，必须在所有页面切换入口统一调用
   - P005中遗漏`switchTab`导致tab切换时状态栏颜色未更新
   - 白名单管理优于分散的条件判断

3. **class和ID必须同步**
   - CSS规则依赖的class必须在HTML中正确添加，否则规则不生效
   - P005中`#page-home`缺少`page-home`类导致header未覆盖状态栏区域
   - 代码生成后必须检查class和ID的对应关系

4. **避免hack方案**
   - 用占位div平衡navbar布局是不合理的hack
   - 应理解flex+absolute定位的本源行为
   - 遇到布局问题先回顾基础定位原理，而非寻找绕过方案

5. **渐变背景不适合做文字对比保障**
   - 渐变底部透明会导致文字在某些背景上不可见
   - 状态栏应使用透明背景+动态文字颜色方案
   - 任何文字对比方案必须在深浅两种背景上验证
