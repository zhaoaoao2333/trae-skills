# PRD 文档编写规范

## 核心定位

PRD 文档有两个作用：
1. 与客户、技术团队沟通功能需求
2. 作为原型生成的唯一输入源

## 编写总则

- **结论先行**：每个模块开头一句话讲清核心内容
- **信息架构不写视觉**：写什么信息、从哪来、怎么更新，不写位置、颜色、字号、间距
- **单层深度**：不嵌套多层目录
- **不展开常识**：不解释行业通用术语
- **不留模糊空间**：所有规则给出明确结论
- **所有问题在进入PRD前已确认**：PRD产出前，阶段三（需求梳理）和阶段四（功能细化）中的所有待确认问题必须全部解决。PRD中**不再包含** `[待PM确认]` 标记或待确认清单
- **确有例外需PM强制**：如PM明确要求保留某项待确认并带入原型阶段，需在该模块标注 `[PM强制保留-待确认]` 并说明原因
- **MVP 优先**：首次交付以跑通核心路径为目标，边缘内容标注 [MVP]

## PRD 五部分结构

### 1. 文档元信息

| 字段 | 说明 |
|------|------|
| 名称 | 文档名称 |
| 项目ID | P+三位数字 |
| 日期 | 编写日期 |
| 版本号 | v1.0 / v1.1 等 |
| 状态 | 草稿 / 评审中 / 已确认 |

### 2. 项目概述

- **背景**：为什么做这个项目
- **建设目标**：要达成什么效果
- **目标用户**：谁在使用
- **项目边界**：
  - 包含：本项目覆盖的范围
  - 不含：明确排除的范围

### 3. 核心业务流程

按角色分步骤端到端描述，覆盖：
- 正向路径（正常操作流程）
- 取消路径（用户中途取消）
- 异常路径（出错、超时、网络异常等）

### 4. 功能模块详细说明

每个模块包含：

| 字段 | 说明 |
|------|------|
| 目的 | 一句话讲清这个模块做什么 |
| 优先级 | 高优（核心操作）/ 中优（辅助信息）/ 低优（补充内容） |
| 信息架构 | 包含哪些信息、层级关系、从哪来、怎么更新 |
| 内容来源 | 数据是用户输入/系统生成/第三方接口 |
| 操作 | 用户可以做什么操作 |
| 业务规则 | 操作的约束条件、校验规则、边界情况 |
| 关联模块 | 与其他模块的交互关系 |

### 5. 原型设计方案

- 端口描述（iOS/Android/Web/小程序）
- 各端导航架构
- 页面优先级（P0/P1/P2/P3）
- 状态矩阵
- 主要交互流程
- 交互行为映射
- 页面呈现方式
- 交互规范总则

## 禁止写的内容

- 位置（顶部/底部/左侧/右侧）
- 排版方式（卡片/列表/表格/几栏）
- 间距、颜色、字号
- 常识性背景、方法论注释
- 编造的竞品数据、技术可行性断言、不存在的案例引用

## PRD 自检清单

PRD 撰写完成后，必须逐项自检：

### 结构自检（5项）

- [ ] 是否符合 PRD 五部分结构（文档元信息/项目概述/核心业务流程/功能模块详细说明/原型设计方案）
- [ ] 是否包含信息架构但不包含视觉描述（不写位置、颜色、字号、间距）
- [ ] 是否有模糊空间（PRD中**不得出现** `[待PM确认]` 标记，所有不确定项必须在阶段三/四内解决）
- [ ] MVP 项是否标注 [MVP]
- [ ] 是否包含常识性废话（如有则删除）

### 内容质检（5项）

- [ ] 信息架构完整性（每个模块的信息来源、更新方式是否明确）
- [ ] 业务流程是否覆盖正向/取消/异常路径
- [ ] 模块间关联是否一致（数据流、依赖关系是否闭环）
- [ ] 与行业规范对比，PRD 内容是否符合标准（如：电商项目是否包含售后、物流等必要模块）
- [ ] 如有行业规范要求但 PRD 未覆盖的板块，列出清单询问 PM 是否需要补充

### 自检通过标准

全部10项检查通过，方可提交PM审阅。未通过项必须修正后重新自检。
