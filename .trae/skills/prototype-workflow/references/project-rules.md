# 项目管理规则

## 项目资产

### 项目ID
- 格式：P + 三位数字（如 P001、P002）
- 由注册表分配，不重复不回收

### 文件夹命名
- 格式：P编号-项目简称-年月（如 P001-电商APP-2606）

### 标准子目录
```
P编号-项目简称-年月/
├── 00-项目记录/     ← 确认记录、断点续传、上下文记忆、版本记录
│   ├── context-memory.md   ← 上下文记忆文件
│   ├── version-log.md      ← 版本记录文件
│   └── *.md                ← 各阶段产出物历史版本
├── 01-需求文档/     ← PRD 文档
├── 04-原型/         ← 原型文件
└── 05-交付物/       ← 最终交付
```

### 项目注册表
- 位置：团队共享根目录
- 按状态分表管理

## 项目初始化

新项目必须先创建文件夹和标准子目录，按规范命名。

## 注册表管理

注册表为唯一真实来源，每次里程碑自动更新状态。

## 上下文管理

- 切换项目必须重置上下文
- 检测到异议主动提醒
- 每次确认写记录到 `00-项目记录/`，上下文断了可无缝恢复

## 上下文记忆管理

### 记忆文件维护

- **位置**：`00-项目记录/context-memory.md`
- **维护者**：AI 自动维护，PM 可查看
- **更新时机**：每个阶段结束时自动追加
- **读取时机**：每个阶段开始时自动读取

### 记忆内容规范

每条记忆记录包含：
- 日期时间
- 阶段名称
- 要点摘要（一句话）
- 详细内容（如有需要）
- 置信度标注（确定/推测/待验证）

### 遗忘检查

生成产出物前，AI 必须：
1. 读取记忆文件
2. 对照检查产出物是否包含所有已确认要点
3. 发现遗漏立即修正
4. 记录修正原因到记忆文件

## 版本回溯管理

### 版本记录维护

- **位置**：`00-项目记录/version-log.md`
- **维护者**：AI 自动维护
- **更新时机**：每次产出物保存时记录

### 版本命名规则

| 版本号变化 | 触发条件 |
|-----------|---------|
| 主版本 +1（v1.0 → v2.0） | 阶段切换时 |
| 次版本 +1（v1.0 → v1.1） | 同一阶段内重大修改 |

### 文件版本保存

- 每个阶段产出物保存为独立文件
- 文件名格式：`[内容]-v[版本号].md`
- 示例：`流程梳理-v1.0.md`、`PRD-v2.0.md`、`原型-v3.0.html`

### 回溯操作规范

1. PM 提出回溯请求（「回溯到 v1.2」）
2. AI 读取版本记录，定位目标版本
3. AI 加载目标版本的产出物
4. AI 确认回溯内容（展示关键差异）
5. PM 确认后，从目标版本继续工作
6. 新版本号接续（回溯到 v1.2 → 新版本 v1.3）
7. 记录回溯操作到版本日志

## 防幻觉规则

| 置信度 | 处理方式 |
|--------|---------|
| 确定 | 直接陈述 |
| 推测 | 标注「待验证」 |
| 未知 | 直接说不知道 |

禁止：
- 编造竞品功能
- 技术断言
- 行业数据
- 不存在的案例

## 项目实战经验（从实际项目沉淀）

> 以下经验来自P001-高速服务区物业等项目的实战经验，是流程规范和设计规范的重要补充。

### 流程经验

1. **Skill加载不可缺失**
   - 项目初始化时必须确认skill已正确加载
   - 如skill未加载或加载错误，产出将严重偏离预期
   - 每次新项目启动时，先检查skill状态

2. **设计纲要不可跳过**
   - 即使PM催促，也必须先输出并确认设计纲要
   - 跳过设计纲要的直接后果：原型方向错误、反复修改
   - 设计纲要是"把设计想清楚"的关键步骤

3. **分阶段边界清晰**
   - 文档阶段（PRD）和原型阶段必须有明确的PM确认节点
   - 不可在PRD未确认时开始原型生成
   - 每个阶段结束必须获得PM确认信号

### 技术经验

1. **SPA导航是Bug高发区**
   - tab-bar显隐、pageStack管理、返回逻辑是原型中最容易出问题的部分
   - 必须建立SPA导航自检清单（8项检查），每次生成后强制执行
   - 常见问题：二级页面未隐藏tab-bar、返回后未显示tab-bar、多page同时active

2. **home-indicator常被忽略**
   - iPhone X及以上机型的home-indicator会遮挡底部导航
   - 需在容器约束规范中明确适配要求
   - 检查方法：在iPhone X模拟器中验证

3. **UI一致性需要铁律**
   - 卡片化、间距、字号必须在设计纲要中显式声明
   - 不同端口（如员工端vs管理端）必须用不同的设计参数
   - 避免用一套设计参数覆盖所有端口

### 迭代经验

1. **v1.0往往不符合预期**
   - 初次生成后必须经过审查→修复→再审查
   - 设计师审查能发现PM遗漏的问题
   - 不要期望一次生成就完美

2. **重新设计有时比修复更快**
   - 当v1.0偏离严重时，重新设计可能更高效
   - P001项目中员工端从v1.0到v3.0的重新设计带来了质的提升
   - 判断标准：修复成本 > 重新设计成本时，选择重新设计

3. **用户群体差异决定设计分化**
   - 同一业务系统的不同端口，因使用者能力不同，应采用不同设计语言
   - 低操作能力用户：极简大字号、单路径、强引导
   - 效率型用户：数据看板、快捷入口、批量操作
   - 设计分化应在设计纲要阶段明确
