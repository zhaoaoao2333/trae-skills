# 原型生成规范（全行业通用）

> 本文件包含所有行业项目通用的原型生成规范。
> 行业特定规范（模块清单、业务规则、页面框架）见 `industry-rules.md`。

---

## 规则编号体系（全行业通用）

设计纲要中所有设计决策必须引用以下规则编号，标注"遵守的规则编号"和"决策依据"。

### 布局规则

| 编号 | 规则内容 | 对应现有章节 |
|------|---------|-------------|
| 布局规则-01 | 页面从上到下按"核心操作→核心内容→辅助信息→延伸推荐"排列 | 页面布局设计原则 |
| 布局规则-02 | 不同功能模块优先用负空间（16-24px留白）区分，避免使用边框 | 页面分区原则 |
| 布局规则-03 | 移动端单列布局，单行内容宽度不超过屏幕宽度的90% | 视口与容器约束 |
| 布局规则-04 | 首页视觉重心放在上半屏（屏幕高度的50%以内），确保首屏可见核心价值点 | 首页布局混合策略 |
| 布局规则-05 | 不同区块必须使用不同布局方式（轮播/网格/横滑/纵向），禁止全部横向滚动 | 首页布局混合策略 |

### 交互规则

| 编号 | 规则内容 | 对应现有章节 |
|------|---------|-------------|
| 交互规则-01 | 信息量小的操作（确认/选择/简短输入≤3项）使用居中弹窗或底部抽屉，不跳转页面 | 弹窗规范 |
| 交互规则-02 | 内容超一屏或多步骤操作使用子页面推入，必须提供返回路径 | 交互闭环规则 |
| 交互规则-03 | 操作成功用Toast轻提示（2s自动消失）；操作失败用当前页提示+明确引导；不可逆操作必须二次确认 | 交互闭环规则 |
| 交互规则-04 | 所有可点击区域不小于44×44pt，按钮点击态缩放至95% | 组件布局规范-按钮 |
| 交互规则-05 | 列表加载优先使用骨架屏，不使用全屏转圈。加载超时10s自动显示重试入口 | 加载状态 |

### 视觉规则

| 编号 | 规则内容 | 对应现有章节 |
|------|---------|-------------|
| 视觉规则-01 | 品牌色仅用于主按钮、选中态、关键标签；不做大面积背景色 | 颜色体系 |
| 视觉规则-02 | 字体层级不超过4级：大标题20px Bold、小标题16px Medium、正文14px Regular、辅助文字12px Light | 字体尺寸体系 |
| 视觉规则-03 | 所有间距基于8px网格系统：元素间8px、模块间16px、页面边距16px、卡片内边距12px | 间距体系 |
| 视觉规则-04 | 同层级组件圆角统一：卡片12px、按钮6px、输入框8px、弹窗16px | 圆角体系 |
| 视觉规则-05 | SVG图标必须设置固定width/height，禁止随容器撑开 | SVG图标与文字容器规范 |

### 状态规则

| 编号 | 规则内容 | 对应现有章节 |
|------|---------|-------------|
| 状态规则-01 | 每个列表页必须覆盖6种状态：常规/空（含引导按钮）/加载（骨架屏）/错误（重试入口）/成功/权限受限 | 页面状态覆盖 |
| 状态规则-02 | 空状态不允许只显示"暂无数据"，必须包含：场景化插图/图标、引导文案（≤两行）、引导操作按钮 | 空状态 |
| 状态规则-03 | 加载态优先使用骨架屏，形状与真实内容一致。超过10s未加载显示"加载失败，点击重试" | 加载状态 |
| 状态规则-04 | 网络错误态提供"点击重试"按钮，并允许用户返回上一页 | 页面状态覆盖 |

### 一致规则

| 编号 | 规则内容 | 对应现有章节 |
|------|---------|-------------|
| 一致规则-01 | 同类型组件（按钮/卡片/弹窗/输入框）在整个产品中样式完全一致，不允许页面级差异 | 组件复用原则 |
| 一致规则-02 | 所有弹窗的关闭方式统一：右上角关闭按钮+点击遮罩关闭+物理返回键关闭 | 弹窗 |
| 一致规则-03 | 文案风格：无称呼（不用"您"），操作动词开头（"点击查看"而非"您可以点击查看"），反馈用陈述句（"已加入购物车"） | — |
| 一致规则-04 | 同一页面在PRD、原型、交互文档中的名称必须完全一致 | — |

## 一、生成前端口确认

生成原型前必须先确认需要覆盖的端口。

端口与设计规范对应：
| 端口 | 设计规范 |
|------|---------|
| iOS | Apple HIG |
| Android | Material Design 3 |
| Web | 响应式标准 |
| 小程序 | 微信小程序规范 |

每个端口独立生成，遵循对应设计规范。

## 二、页面风格确认

生成页面之前，必须先确认页面风格。

### 风格确定流程

1. 根据行业类型和项目背景，给出 2-3 个风格方案
2. 每个方案包含：整体风格、主色调、辅助色、字体风格、参考案例
3. PM 确认后锁定风格，后续所有页面统一使用

### 行业风格指南

| 行业 | 风格特征 | 色调倾向 | 设计侧重点 |
|------|---------|---------|-----------|
| 商城/电商 | 鲜明、促销感强 | 红色/橙色/品牌色 | 商品展示、购买引导、优惠信息突出 |
| 信息发布 | 简洁、层次清晰 | 蓝色/灰色/白色 | 内容阅读体验、信息层级分明 |
| 企业服务 | 专业、克制 | 蓝色/深灰/白色 | 数据展示、操作效率、可信感 |
| 社交 | 活泼、亲和 | 多彩/渐变/品牌色 | 互动氛围、用户表达、即时反馈 |
| 金融 | 严谨、稳重 | 深蓝/金色/白色 | 安全感、数据准确、合规感 |
| 教育 | 清新、友好 | 绿色/蓝色/暖色 | 学习氛围、进度可视化、互动感 |
| 医疗 | 安静、可信 | 蓝绿色/白色/浅灰 | 信息准确、操作简单、隐私感 |
| O2O/本地生活 | 亲切、便捷 | 橙色/绿色/品牌色 | 位置服务、商家展示、快速下单 |

## 三、先结构后页面

生成页面之前，必须先梳理页面结构：

1. **页面树**：列出所有页面的层级关系（登录→主导航→二级→三级）
2. **页面清单**：每个页面标注优先级、类型、核心内容
3. **交互关系图**：页面间的跳转关系

**页面结构经 PM 确认后，才能开始生成页面。**

## 四、逐级闭环生成

按页面层级逐级生成，**每级生成后必须形成完整交互闭环**。

### 生成顺序

| 级别 | 页面 | 闭环要求 |
|------|------|---------|
| 第一级 | 登录/注册、启动页 | 登录成功后能跳转到主导航 |
| 第二级 | 底部导航各 TAB 主页 | TAB 间可切换，入口链接可点击，未生成的显示 Toast |
| 第三级 | 二级页面 | 从主导航可跳转，有返回路径，操作链接有效 |
| 第四级 | 三级页面 | 同上，返回路径完整 |

### 闭环规则

- **已生成的页面**：正确跳转
- **未生成的页面**：Toast 提示「页面正在建设中，即将上线」
- **每级生成后**：已生成的所有页面之间必须形成完整交互闭环
- **禁止死链**：所有可点击元素都必须有响应，不允许点击无反应
- **每级内按优先级**：P0 → P1 → P2 → P3

## 五、导航架构设计原则

### 核心原则：从用户视角设计导航，而非系统模块视角

**禁止做法**：
- ❌ 直接把系统模块名作为底部导航 TAB（如：订单管理、用户中心、数据报表）
- ❌ 底部导航放超过5个 TAB
- ❌ 把后台功能入口放在一级导航

**正确做法**：
- ✅ 底部导航从**用户的使用视角**出发（如：首页、发现、消息、我的）
- ✅ 业务模块入口放在**首页金刚区**（如：商城→用金刚区图标承载"商品""订单""优惠券"）
- ✅ 次要功能放在**我的页面**的列表菜单中
- ✅ 底部导航不超过4-5个，必须是用户最常切换的视角

### 底部导航设计规则

| 要求 | 规范 |
|------|------|
| TAB 数量 | 3-5个，推荐4个 |
| 命名方式 | 用户视角词（首页/发现/消息/我的），非模块名 |
| 图标 | 选中态实心 / 非选中态线框 |
| 高度 | 56pt |
| 切换 | 不支持滑动切换 |

**TAB 常见组合**：

| 项目类型 | 推荐 TAB 组合 |
|---------|--------------|
| 电商 | 首页 / 分类 / 购物车 / 我的 |
| 内容社区 | 首页 / 发现 / 发布（+） / 消息 / 我的 |
| 企业服务 | 工作台 / 消息 / 我的 |
| 社交 | 首页 / 发现 / 消息 / 我的 |
| 社区服务（C端） | 首页 / 周边 / 社区 / 我的 |
| 工具类 | 首页 / 功能 / 我的 |

**消息/通知放置原则**：

| 项目场景 | 放置位置 | 设计方式 |
|---------|---------|---------|
| 消息是核心功能（社交/社区/企服） | 底部导航 | 独立TAB「消息」，带未读红点 |
| 消息是辅助功能（电商/工具/社区服务） | 顶部导航栏 | 右侧铃铛图标 + 未读数字角标 |
| 消息是辅助功能 + **小程序端口** | 底部导航 | 独立TAB「消息」或金刚区入口 |

> **注意**：小程序端口下，即使消息是辅助功能，也不能放顶部导航栏右侧（与胶囊按钮冲突），必须放底部导航或金刚区。

**顶部铃铛设计规范**：
```css
.header-bell {
  position: relative;
  width: 24px; height: 24px;
}
.header-bell .badge {
  position: absolute;
  top: -2px; right: -4px;
  min-width: 16px; height: 16px;
  background: #ff4d4f;
  color: #fff;
  font-size: 10px;
  border-radius: 8px;
  text-align: center;
  line-height: 16px;
}
```
- 位置：顶部导航栏右侧
- 铃铛图标24px，灰色
- 未读数角标：红色圆形，最小16px

### 首页金刚区设计规则

金刚区是首页的核心导航区，承载业务模块入口：

- **位置**：首页顶部，Banner 下方
- **数量**：单行4-5个，总数8-10个（两行）
- **图标**：40-48px，风格统一
- **文字**：12-13px，居图标下方
- **内容**：业务核心入口（如商城→商品、订单、优惠券、收藏）

**金刚区入口规划原则**：
- 放用户最常用的业务操作入口
- 不是所有模块都要进金刚区，按使用频率筛选
- 剩余的放在「全部功能」或「我的」页面

### 我的页面菜单设计规则

「我的」页面承载次要功能和设置：

- 顶部：用户头像、昵称、ID
- 中部：列表菜单（订单、收藏、优惠券、地址等）
- 底部：设置、关于、退出登录

### 顶部导航栏

| 端口 | 高度 | 特殊规范 |
|------|------|---------|
| iOS | 44pt | 无 |
| Android | 56dp | 无 |
| Web | 56px | 无 |
| 小程序 | 44px | **右上角胶囊按钮区域禁止放置任何内容** |

**小程序顶部导航栏特殊规范 🔴**：

微信小程序右上角有固定的系统胶囊按钮（返回/更多/关闭），该区域**绝对不能放置任何内容**：

```
┌────────────────────────────┐
│  ← 返回      页面标题       │ [胶囊按钮区] │
│                             │  [..] [○]   │ ← 系统固定，不可覆盖
└────────────────────────────┘
              ↑
         右侧约90px为胶囊区，禁止放置图标/文字/按钮
```

**小程序导航栏设计规则**：
- 标题必须居中或左对齐，**不能延伸到右侧胶囊区**
- 导航栏右侧**禁止**放置消息铃铛、搜索、分享、更多操作等图标
- 如需这些功能，必须移至其他位置：
  - 消息铃铛 → 底部导航「消息」Tab 或 金刚区入口
  - 搜索 → 金刚区入口 或 页面内搜索框
  - 分享/更多 → 页面内按钮 或 底部操作栏

**各端口顶部功能入口放置对照**：

| 功能 | iOS/Android/Web | 小程序 |
|------|----------------|--------|
| 消息/通知 | 顶部导航栏右侧铃铛 | 底部导航「消息」Tab |
| 搜索 | 顶部导航栏右侧搜索图标 | 金刚区入口 或 页面内搜索框 |
| 分享 | 顶部导航栏右侧分享图标 | 页面内按钮/底部操作栏 |
| 更多操作 | 顶部导航栏右侧更多图标 | 页面内按钮/底部操作栏 |
| 设置 | 顶部导航栏右侧设置图标 | 「我的」页面列表项 |

## 六、功能拆分与合并判断原则

在梳理页面结构和导航时，必须判断功能是独立展示还是合并：

### 拆分判断标准

| 判断维度 | 应拆分（独立Tab/独立页面） | 可合并（子Tab/同一页面） |
|---------|--------------------------|------------------------|
| 用户心智模型 | 用户认为是两件不同的事 | 用户认为是同一件事的不同形式 |
| 内容性质 | 公开内容 vs 隐私内容 | 同性质、同受众 |
| 使用频率 | 都是高频操作 | 有主次之分 |
| 信息架构 | 内容结构差异大 | 内容结构相似 |

### 禁止的合并场景

- ❌ **公开交流 + 隐私问答**：论坛和问答是两种不同性质的板块，合并导致信息层级混乱
- ❌ **个人信息 + 系统设置**：用户查看和修改的频次、场景不同
- ❌ **核心业务操作 + 辅助工具**：主次不分，降低核心功能访问效率

### 合并后必须做的

如果确实需要合并（如子Tab切换），必须：
- 有清晰的视觉区分（Tab切换、分区标题）
- 用户能一眼看出当前在哪个子区域
- 两个子区域的内容不互相干扰

## 七、统一设计 Token

所有页面必须使用以下统一设计 Token，不得随意使用其他数值。

### 间距体系（以4px为基准）

| Token | 值 | 用途 |
|-------|----|------|
| xs | 4px | 组件内部紧密间距 |
| sm | 8px | 组件内部常规间距 |
| md | 12px | 组件间间距 |
| lg | 16px | 区块内边距、卡片内边距 |
| xl | 20px | 区块间距 |
| xxl | 24px | 大区块间距、页面左右边距 |
| xxxl | 32px | 页面顶部/底部留白 |

### 字体尺寸体系

| Token | 值 | 用途 |
|-------|----|------|
| caption | 11px | 辅助说明文字 |
| mini | 12px | 金刚区文字、标签 |
| body-sm | 13px | 次要正文、描述文字 |
| body | 14px | 正文、列表项文字 |
| body-lg | 15px | 列表标题、卡片标题 |
| subtitle | 16px | 区块标题、导航标题 |
| title | 18px | 页面标题、弹窗标题 |
| headline | 20px | 大标题、金额 |
| display | 24px | 重要数字、Banner标题 |

### 图标尺寸体系

| Token | 值 | 用途 |
|-------|----|------|
| icon-sm | 16px | 行内图标、标签图标 |
| icon-md | 20px | 列表项图标、按钮内图标 |
| icon-lg | 24px | 导航图标、输入框图标 |
| icon-xl | 40-48px | 金刚区图标 |

### 圆角体系

| Token | 值 | 用途 |
|-------|----|------|
| radius-sm | 4px | 小型组件（标签、徽章） |
| radius-md | 8px | 卡片、输入框、按钮 |
| radius-lg | 12px | 弹窗、大卡片 |

## 八、视口与容器约束

### 手机原型容器（HTML实现）

HTML原型必须使用固定宽度的手机容器，禁止直接全屏铺开：

```css
/* 手机框架 */
.phone-frame {
  width: 375px;           /* 固定宽度 */
  max-width: 100vw;       /* 小屏幕自适应 */
  height: 812px;          /* 固定高度 */
  max-height: calc(100vh - 40px);  /* 自适应视口高度，防止底部被裁 */
  margin: 0 auto;         /* 居中显示 */
  overflow: hidden;       /* 禁止超出 */
  position: relative;
  border-radius: 20px;    /* 手机圆角 */
  box-shadow: 0 0 30px rgba(0,0,0,0.15);
}

/* 页面内容区 */
.page-content {
  height: calc(100% - 56px);  /* 减去底部导航高度 */
  overflow-y: auto;           /* 内容区域滚动 */
  -webkit-overflow-scrolling: touch;
}

/* Flex 布局防重叠 */
.content-area,
.page-inner {
  min-height: 0;    /* 必须设置，防止flex子元素被内容撑开 */
}

.page {
  overflow: hidden; /* 防止内容溢出 */
}
```

.bottom-nav {
  position: absolute;      /* 在phone-frame内绝对定位，非fixed */
  bottom: 0;
  left: 0;
  right: 0;
  width: 100%;             /* 相对phone-frame */
  height: 56px;
  z-index: 1000;           /* 必须足够高，不能被页面内容层覆盖 */
}
```

.modal-overlay {

  top: 0; left: 0; right: 0; bottom: 0;
  background: rgba(0,0,0,0.5);
  z-index: 2000;           /* 高于底部导航 */
}
```

### Z-Index 层级规范

为防止组件互相覆盖，统一使用以下 z-index 层级：

| 层级 | z-index | 组件 |
|------|---------|------|
| 基础层 | 1 | 页面内容 (.page) |
| 中层 | 100 | 搜索建议、下拉菜单、页面内浮动元素 |
| 导航层 | 1000 | 底部导航 (.tab-bar)、悬浮按钮 (.fab) |
| 遮罩层 | 2000 | 弹窗遮罩 (.modal-overlay) |
| 弹窗层 | 2100 | 弹窗内容 (.modal-content) |
| 提示层 | 3000 | Toast 提示 (.toast) |

### Z-Index 强制声明规则 🔴

**所有设置了 `position: absolute` 或 `position: relative` 的元素，必须显式声明 `z-index`**：

```css
/* ❌ 禁止 — 缺 z-index */
.page-content { position: absolute; top: 44px; }

/* ✅ 正确 — 显式声明 z-index */
.page-content { position: absolute; top: 44px; z-index: 1; }
```

**为什么必须强制声明**：
- 缺少 z-index 的元素可能被其他元素意外遮挡
- 浏览器对无 z-index 元素的层叠顺序依赖 DOM 顺序，不可预测
- 组件在不同页面中 DOM 顺序不同，无 z-index 的行为不一致

### Z-Index 排查清单

当出现组件被遮挡时，按以下顺序排查：

1. **核心容器**：`.phone-frame`(z-index:0) → `.page`(z-index:1) → `.page-content`(z-index:1) — 基础层必须显式声明
2. **FAB 按钮**：确认 z-index 为 100，不能低于任何 `.page-content` 内的元素
3. **底部 Tab-bar**：确认 z-index 为 1000，所有页面内元素 z-index 必须 < 1000
4. **弹窗遮罩**：确认 z-index 为 2000，弹窗内容 z-index 为 2100
5. **扫描冲突**：全局搜索 `z-index`，确认所有值都在规范范围内（1/100/1000/2000/2100/3000），不允许使用其他值
6. **重复定义**：同一个 z-index 值被用于多个可能互相覆盖的元素 → 调整到不同层级

### 关键约束规则

- **所有元素**必须在 phone-frame 内部，使用 `position: absolute` 或相对定位
- **严禁使用 `position: fixed`**（fixed 相对于视口，会超出 phone-frame）
- **底部导航**：`position: absolute; bottom: 0;`
- **弹出层**：`position: absolute;` 覆盖 phone-frame 全区域
- **内容滚动**：只在 page-content 内滚动，phone-frame 禁止滚动

## 十一、页面布局设计原则

### 核心原则：每个页面必须有设计感，而非功能罗列

**禁止做法**：
- ❌ 页面只是一个列表，从上到下堆砌所有功能入口
- ❌ 所有内容同样大小、同等权重，没有视觉层次
- ❌ 没有分区、没有标题、没有留白，内容挤在一起
- ❌ 只用纯文字，没有图标、配图、色彩点缀

**正确做法**：
- ✅ 页面按功能分区，每个区域有明确的标题和视觉边界
- ✅ 核心内容突出（大图、强调色），次要内容弱化（小字、浅色）
- ✅ 善用留白和分割线区分不同内容区
- ✅ 图文结合，用图标和色彩增强辨识度

### 视觉层次法则

每个页面必须建立三层视觉层次：

| 层次 | 用途 | 实现方式 |
|------|------|---------|
| 第一层 | 最想让用户看到的内容 | 大字体（18-24px）、品牌色、大图、Banner |
| 第二层 | 主要内容、操作入口 | 常规字体（14-16px）、卡片、金刚区图标 |
| 第三层 | 辅助信息、补充内容 | 小字体（11-13px）、灰色文字、列表项描述 |

### 页面分区原则

- **每个页面至少3-4个视觉分区**（Banner区、金刚区、内容区、推荐区等）
- **分区之间**用留白（20-24px）或浅色背景区分
- **分区标题**：16px 加粗 + 左侧色条或图标点缀
- **不要把所有内容挤在一起**，善用留白创造呼吸感

### 图文结合原则

- **每个功能入口配备图标**（金刚区图标、列表项左侧图标）
- **卡片内容配备配图**（商品图、文章封面图、用户头像）
- **图标风格统一**（同一套图标风格：线性/面性/双色，二选一）
- **无图片时使用占位图**（灰色背景+居中图标，而非空白）

### 首页布局混合策略

首页不同区块必须使用不同的布局方式，避免全部横向滚动导致视觉单调：

| 区块类型 | 推荐布局 | 原因 | 数量控制 |
|---------|---------|------|---------|
| Banner | 轮播 | 运营位，需要大图展示 | 3-5张 |
| 金刚区 | 网格（2行x4-5列） | 功能入口，一目了然 | 8-10个 |
| 限时/特惠 | 横向滚动 | 紧迫感，快速浏览 | 3-4个卡片 |
| 附近推荐 | 横向滚动 | 激发探索欲 | 3-4个卡片 |
| 热帖/内容 | 纵向列表 | 内容需要阅读，纵向更适合 | 2-3条+"更多" |
| 问答/知识 | 纵向列表 | 内容需要阅读，纵向更适合 | 2-3条+"更多" |
| 分类/标签 | 横向滚动 | 筛选功能，快速切换 | 一行 |

**禁止**：首页所有区块全部采用同一种布局方式（如全部横向滚动）。

### 行业布局参照规范

生成页面布局前，必须参照行业头部APP的成熟布局模式：

| 页面类型 | 参照APP | 核心结构 |
|---------|---------|---------|
| 电商首页 | 淘宝/拼多多/美团 | Banner→金刚区→分类Tab→推荐列表 |
| 周边/本地生活 | 美团/大众点评 | 搜索→分类Tab→筛选→门店卡片列表 |
| 社区/内容Feed | 小红书/微博 | 顶部Tab→Feed流卡片→底部互动栏 |
| 商品详情 | 淘宝/拼多多 | 大图轮播→价格→规格→评价→详情→底部操作栏 |
| 发布页 | 小红书/微博 | 返回+标题→文本输入→图片上传→底部发布按钮 |
| 个人中心 | 美团/淘宝 | 用户信息→快捷入口→列表菜单→设置 |

│                      │ 最小高度200px

├──────────────────────┤

**发布页设计要点**：
- 顶部导航：左侧返回箭头 + 居中标题"发布帖子"，**禁止右上角再放发布按钮**（与底部按钮重复）
- 文本输入区：大面积输入框，placeholder提示文字，最小高度200px
- 图片上传：九宫格布局，每张80-100px正方形，1:1比例
- 底部发布按钮：固定底部，与屏幕底部保持至少16px安全距离

**执行要求**：
1. 生成前先明确告知PM参照的APP和页面结构
2. 自检时对照上表检查布局是否符合行业惯例
3. 同一容器内的卡片类型必须保持一致（禁止不同类型卡片混排）

### 组件复用原则

**同一组件在不同页面中必须保持样式一致**，禁止为不同页面做两套样式：

- 首页热帖卡片 必须复用 社区页帖子卡片样式
- 商品卡片在首页/列表页/搜索结果页 必须保持一致
- 用户信息卡片在多处使用时 必须保持一致

**为什么必须复用**：
- 减少前端开发工作量（一套样式+适配）
- 保持用户体验一致性
- 降低维护成本

## 十二-B、表单设计规范

### 表单数据保护

- **必须**实现表单数据本地缓存机制（如 `localStorage` 或 JS 变量缓存）
- 用户填写表单后切换页面再返回，已填内容不得丢失
- 页面跳转前自动保存草稿，返回时自动恢复

```javascript
// 表单缓存示例
let formDataCache = {};

function saveFormData(formId, data) {
  formDataCache[formId] = data;
}

function restoreFormData(formId) {
  return formDataCache[formId] || null;
}
```

### 表单布局规范

- 输入框左右间距：`margin: 0 16px`（与页面边距一致）
- 输入框高度：44-48px
- 输入框圆角：8px
- 输入框内边距：`padding: 0 12px`
- 标签文字：14px，位于输入框上方或左侧
- 必填项标记：红色星号 *
- 错误提示：输入框下方12px红色文字

## 十四、输出格式规范

### 方案A：多文件开发 + 单文件打包（推荐）

#### 开发阶段（多文件）

开发期使用多文件项目结构，便于修改和维护：

```
原型项目/
├── index.html              ← 入口文件（加载路由+公共样式）
├── pages/                  ← 页面文件
│   ├── home.html
│   ├── goods-list.html
│   ├── goods-detail.html
│   ├── cart.html
│   ├── order-list.html
│   └── profile.html
├── components/             ← 公共组件
│   ├── nav-bar.html
│   ├── tab-bar.html
│   └── toast.html
├── css/
│   └── common.css          ← 公共样式（Token定义）
└── js/
    └── router.js           ← 路由逻辑
```

**多文件开发规范**：
- 每个页面独立一个 HTML 文件
- 公共组件（导航栏、底部Tab、Toast）放在 components/
- 公共样式（CSS变量、工具类）放在 css/common.css
- 路由逻辑放在 js/router.js，使用 hash 路由
- 页面间跳转：`navTo('goods-list')` → 改变 hash → 加载对应页面

#### 打包阶段（单文件）

PM 终审确认后，打包成单个 HTML 文件用于分享：

```
dist/
└── index.html              ← 单文件，内嵌所有内容
```

**打包方式**：
- 方式1：AI 使用脚本自动合并（内嵌 CSS + 内嵌 JS + 页面内容合并）
- 方式2：使用 Vite 等构建工具（`npm run build`）
- 方式3：手动复制粘贴合并（兜底方案）

**打包后检查**：
- [ ] 单个 HTML 文件，无外部依赖
- [ ] 浏览器直接打开可正常预览
- [ ] 所有页面跳转正常
- [ ] 所有样式生效

### 方案B：单文件开发（简单项目）

对于页面少、逻辑简单的项目，可直接使用单文件：

- 使用内嵌 CSS（`<style>` 标签）
- 使用内嵌 JavaScript（`<script>` 标签）
- 页面切换通过 JS 控制显示/隐藏
- 图片资源使用内嵌 Base64 或 CSS 绘制

### 技术实现要点

#### Hash 路由（多文件方案）

```javascript
// router.js
function navTo(page) {
  window.location.hash = '#' + page;
}

window.onhashchange = function() {
  const page = location.hash.slice(1) || 'home';
  loadPage(page);  // 异步加载 pages/xxx.html 内容
};

function goBack() {
  history.back();
}
```

#### 页面加载（多文件方案）

```javascript
function loadPage(pageName) {
  // 隐藏所有页面
  document.querySelectorAll('.page').forEach(p => p.classList.remove('active'));
  
  // 加载目标页面内容（从 pages/ 目录）
  fetch(`pages/${pageName}.html`)
    .then(r => r.text())
    .then(html => {
      document.getElementById('page-container').innerHTML = html;
      // 标记当前页面激活
      document.querySelector('.page').classList.add('active');
    });
}
```

#### 公共组件复用（多文件方案）

```javascript
// 在每个页面加载时注入公共组件
function injectComponents() {
  // 注入顶部导航
  document.getElementById('nav-bar').innerHTML = getNavBarHTML();
  // 注入底部Tab
  document.getElementById('tab-bar').innerHTML = getTabBarHTML();
}
```

### HTML 产出物自检清单

**每次生成 HTML 后，必须强制执行以下8项检查（子Agent生成后主Agent校验）：**

1. **脚本完整性**：所有 JS 代码必须在 `<script>` 标签内，body 中不得有裸露的 JS 代码文字
2. **无重复块**：不得有重复的 `<style>` 或 `<script>` 块，每个类型只保留一个标签
3. **核心函数唯一**：`navTo()`、`goBack()`、`showToast()`、`switchTab()` 等核心函数仅定义一次
4. **DOM 完整性**：核心元素（navBar、tabBar、toast、modalOverlay）必须存在，`.page.active` 规则必须包含 `display: block`
5. **Design Token 合规**：所有图标/图片/间距/字体尺寸必须符合Token规范（图标16-64px、间距4-32px、字体11-24px）
6. **SVG 与文字容器**：所有SVG图标设置固定width/height；单行文字容器设置 `white-space: nowrap`
7. **滚动条隐藏**：所有滚动区域已添加滚动条隐藏CSS
8. **实机预览验证**：浏览器打开确认无白屏、无乱码、无控制台报错、无布局失调

**检查流程**：
1. 子Agent生成 HTML → 保存到 `04-原型/`
2. 主Agent 读取文件 → 执行5项检查
3. 不通过 → 返回子Agent修复
4. 通过 → 交付 PM 预览

**批量修复脚本风险检查**（新增）：
- 使用正则批量替换时，必须保护复合CSS规则（多属性在同一行）
- **禁止**使用简单正则替换多属性CSS规则，如 `.page.active { display: block; z-index: 10; }` 不能仅替换 `z-index` 而丢失 `display`
- 修复后必须执行实机预览验证，确认页面可见
- `.page.active` 等关键规则必须加入DOM完整性检查
- **推荐**：修复脚本使用AST解析CSS，而非正则替换

### 浏览器兼容性注意事项

- SVG 图标颜色控制：使用 `fill="currentColor"` / `stroke="currentColor"` + CSS `color` 属性，**禁止**在 SVG 属性中直接使用 CSS 变量（`fill="var(...)"`，兼容性差）
- 正确写法：`.tab-item.active .tab-icon { color: #FF6B35; }` 配合 `<path fill="currentColor">`
- Flexbox：flex 容器内的子元素需显式设置 `min-height:0`，防止内容撑开导致布局错乱

### 图片比例规范

| 图片类型 | 推荐比例 | 说明 |
|---------|---------|------|
| 电商商品图 | 1:1（正方形） | 行业通用标准，淘宝/拼多多/美团均采用 |
| 商品详情大图 | 1:1 或 3:4 | 展示商品全貌 |
| Banner/轮播 | 16:9 或 2:1 | 运营位大图 |
| 用户头像 | 1:1（圆形） | 统一圆形裁剪 |
| 内容封面 | 16:9 或 4:3 | 文章/帖子封面 |
| 店铺头图 | 16:9 | 商家展示 |

**禁止**：商品图片使用非1:1比例（如长方形），导致与行业惯例不符。

### SVG图标与文字容器规范

**SVG图标必须设置固定尺寸**，禁止随容器撑开：

```css
/* ✅ 正确 — 固定尺寸 */
.arrow-icon {
  width: 16px;
  height: 16px;
  flex-shrink: 0;  /* 防止被挤压 */
}

/* ❌ 禁止 — 无固定尺寸，可能撑大到80px+ */
.arrow-icon {
  /* 缺少 width/height */
}
```

**文字容器必须防止意外换行**：

```css
/* 单行文字（店名、标题等） */
.text-ellipsis {
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}

/* 多行文字（正文、描述等） */
.text-multi {
  display: -webkit-box;
  -webkit-line-clamp: 2;
  -webkit-box-orient: vertical;
  overflow: hidden;
}
```

### 滚动条隐藏

移动端原型必须隐藏原生滚动条（真实APP无滚动条）：

```css
.page-content::-webkit-scrollbar {
  display: none;
}
.page-content {
  scrollbar-width: none;
  -ms-overflow-style: none;
}
```

## 十六、设计纲要规范

### 设计纲要定义

设计纲要是规则的"项目化实例"。规则是全行业通用的，纲要是把通用规则应用到具体项目后产生的结果。

**设计纲要在PRD确认后、原型生成前输出**，是AI写代码前必须完成的设计思考过程。

### 设计纲要8章节

| 章节 | 内容 | 输出要求 |
|------|------|---------|
| 1. 产品设计基调 | 设计关键词（3-5个）、设计目标（基于PRD翻译）、风格参照（具体产品参考）、遵守的规则编号 | 基于PRD提取，AI主动推荐 |
| 2. 布局架构 | 导航体系（端口/导航方式/选择依据/TAB数量/名称）、关键页面布局（每页标注遵守的规则编号） | 每个区块标注规则编号和决策依据 |
| 3. 交互设计 | 容器选择标准（场景→容器类型→决策依据）、核心交互流程（覆盖正向/取消/异常路径）、加载与刷新 | 每个交互场景标注规则编号 |
| 4. 视觉规范 | 色彩系统（具体十六进制色值）、字体体系（≤4级）、间距系统（基于8px网格）、组件样式 | 具体到数值，不模糊描述 |
| 5. 状态覆盖计划 | 全局状态矩阵（每页面逐行检查）、关键空状态设计（引导文案+按钮） | 逐页面标注覆盖情况 |
| 6. 一致性自查 | 组件/交互/文案/命名一致性检查 | 逐项自查，发现不一致标注修正 |
| 7. AI补充项清单 | AI主动补充的设计细节 | 标注依据规则，全部标注"待确认" |
| 8. 待确认项 | PM需要决策的问题 | 给出方案A/B和推荐 |

### 设计纲要质量标准

生成后必须自检：
- [ ] 每个页面有明确的定位和布局参照（参照哪个APP的哪个页面）
- [ ] 每个设计决策标注了"遵守的规则编号"和"决策依据"
- [ ] 每个页面有视觉层次（三层内容：强调/主体/辅助）
- [ ] 每个页面有隐含功能（至少补充2-3个PRD未提及的功能）
- [ ] 交互组件覆盖完整（至少包含5种交互组件）
- [ ] AI补充项全部标注"待确认"
- [ ] 设计决策有原因（每个决策都有用户场景或业务目标支撑）

## 十七、交互补全清单

### 规则

**每个页面生成时，必须对照以下清单逐项检查，缺失的必须补充。**

设计纲要中规划的交互组件必须实现，未规划的交互组件如发现缺失也必须补充。

### 14项必检交互

| # | 检查项 | 说明 | 不补充的后果 |
|---|--------|------|-------------|
| 1 | 页面跳转 | 所有可点击元素都有跳转目标 | 死链，用户无法继续操作 |
| 2 | 返回路径 | 所有非顶层页有返回按钮 | 页面困死，用户无法返回 |
| 3 | 中部弹窗 | 选择/确认/提示类用中部弹窗 | 只有页面跳转，操作笨重 |
| 4 | 底部弹窗 | 筛选/分享/更多用底部弹窗 | 占用全屏，体验差 |
| 5 | ActionSheet | 操作菜单用底部弹出 | 按钮堆砌，界面混乱 |
| 6 | Toast反馈 | 操作成功/失败用Toast | 用户不知道操作结果 |
| 7 | 加载状态 | 数据加载时骨架屏/动画 | 白屏，用户以为卡死 |
| 8 | 空状态 | 无数据时引导用户 | 空白页面，用户困惑 |
| 9 | 错误状态 | 网络错误/加载失败 | 报错，用户无法继续 |
| 10 | 下拉刷新 | 列表页支持下拉刷新 | 数据陈旧，用户手动退出重进 |
| 11 | 上拉加载 | 列表页支持上拉加载更多 | 只能看第一页数据 |
| 12 | 左滑操作 | 列表项支持左滑删除/收藏 | 必须点击进入详情才能操作 |
| 13 | 搜索功能 | 列表页/内容页必须有搜索 | 用户无法快速找到目标 |
| 14 | 筛选排序 | 列表页必须有筛选和排序 | 信息过载，用户无法定位 |

### 每页交互补全记录表

每条交互项完成后，在记录中标记状态：

```
交互补全记录 - [页面名称]
- [x] 页面跳转：全部可点击元素有跳转目标
- [x] 返回路径：有返回按钮，路径正确
- [ ] 中部弹窗：无（该页面无确认/选择/提示场景）
- [x] 底部弹窗：筛选条件使用底部弹窗
- [x] ActionSheet：更多操作使用ActionSheet
- [x] Toast反馈：加入购物车/收藏操作有Toast
- [x] 加载状态：列表骨架屏
- [x] 空状态：搜索无结果时展示引导
- [ ] 错误状态：无（该页面无网络请求场景）
- [x] 下拉刷新：列表页支持
- [x] 上拉加载：列表页支持
- [x] 左滑操作：收藏列表支持左滑删除
- [x] 搜索功能：列表页顶部搜索框
- [x] 筛选排序：按价格/销量/综合排序
```

## 十八、质量评分标准

### 规则

**生成后不直接交付PM，先进行"质量评分"，低于80分自动修复。**

### 评分维度

| 维度 | 权重 | 评分标准 | 扣分项 |
|------|------|---------|--------|
| 设计感 | 25分 | 布局合理、视觉层次清晰、留白恰当 | 布局单调（-10）、无视觉层次（-10）、拥挤无留白（-5） |
| 交互完整性 | 25分 | 交互补全清单14项覆盖率≥80% | 缺中部弹窗（-5）、缺底部弹窗（-5）、缺Toast（-5）、缺加载（-5）、缺空状态（-5） |
| 行业符合度 | 20分 | 与设计纲要中的参照APP一致 | 未参照行业APP（-10）、布局模式不符（-10） |
| 功能完整性 | 20分 | PRD+设计纲要功能100%实现 | PRD功能缺失（-10/个）、纲要缺失（-5/个） |
| 代码质量 | 10分 | 无报错、无死链、Token合规 | 控制台报错（-5）、死链（-3/个）、Token违规（-2/个） |

### 评分规则

| 分数区间 | 处理方式 |
|---------|---------|
| 90-100分 | 优秀，直接交付PM |
| 80-89分 | 良好，交付PM |
| 70-79分 | 及格，自动修复后重新评分 |
| 60-69分 | 不及格，返回检查设计纲要 |
| <60分 | 严重问题，重新生成 |

### 评分输出示例

```
质量评分报告
============
设计感：20/25（布局合理，但留白不够充分 -5）
交互完整性：22/25（缺左滑操作 -3）
行业符合度：18/20（已参照美团布局）
功能完整性：18/20（缺搜索功能 -2）
代码质量：10/10
总分：88/100
判定：良好，交付PM
```
