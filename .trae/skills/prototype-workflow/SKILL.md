# Prototype Workflow

从需求到原型的完整工作流，分六阶段执行。PRD 文档是原型的唯一输入源。

## 核心原则

1. **PM 驱动**：任何环节 PM 未确认，禁止进入下一步。AI 不替 PM 做决定。
2. **主 Agent 只决策审核，不动手**：文档、原型全部由子 Agent 产出。
3. **先理解再动手**：收到需求先复述、做完整性检查、评估新鲜度，PM 确认后才开始。
4. **防幻觉**：标注置信度（确定/推测/未知），不编造数据。
5. **断点续传**：每次确认写记录到 `00-项目记录/`，上下文断了可无缝恢复。
6. **MVP 优先**：首次交付以跑通核心路径为目标，边缘内容标注 [MVP]。
7. **每步复核质检**：每个阶段/步骤结束后，必须复核产出物是否符合行业规范和标准，发现偏差立即修正。
8. **行业规范反问**：对照行业规范检查是否有遗漏板块，如有则主动询问 PM 该项目是否需要。
9. **输出格式确认**：任何文件输出前，必须先询问 PM 需要的格式（标准PRD/Markdown/HTML/其他）。
10. **输出合规**：所有产出物必须符合对应行业规范和标准。
11. **逐级闭环生成**：页面按层级逐级生成（登录→主导航→二级→三级），每级生成后必须形成完整交互闭环。
12. **先结构后页面**：设计时先梳理页面结构（页面树/层级关系），确认后再生成页面。
13. **项目经验沉淀**：每次项目结束后，整理本次项目的规范性要求，形成技能表。如有需要可补充到技能库中，行业特性类需写明适用行业和调用节点。
14. **上下文记忆**：自动整理并记忆项目过程中的所有关键要点，后续生成过程中持续引用，不遗忘已确认的内容。
15. **版本回溯**：每个阶段产出物保存版本记录，如出现问题可回溯到之前任意版本。

## 触发条件

- PM 声明"新项目"
- 用户需要制作原型
- 用户需要编写 PRD
- 用户从需求出发进行产品设计
- 用户提到"原型""PRD""需求文档""产品设计"等关键词

## 引用规则

执行过程中，根据当前阶段加载对应规则文件：

- **阶段三（需求梳理）和阶段四（功能细化）**：自动调用 `requirement-analysis` 技能
- **阶段五（PRD 产出）**：加载 `references/prd-rules.md`
- **阶段六（原型生成）**：加载 `references/prototype-rules.md`（全行业通用规范）+ `references/industry-rules.md`（行业特定规范，根据项目类型加载对应章节）
- **全局适用**：加载 `references/priority-rules.md`、`references/project-rules.md`

## 阶段一：项目启动

### 步骤 1.1 — 新项目声明

当 PM 表示"接下来是一个新项目"时：

1. 分配项目ID（P+三位数字，从注册表获取）
2. 创建项目文件夹，命名格式：`P编号-项目简称-年月`
3. 创建标准子目录：
   ```
   P编号-项目简称-年月/
   ├── 00-项目记录/     ← 确认记录、断点续传
   ├── 01-需求文档/     ← PRD 文档
   ├── 04-原型/         ← 原型文件
   └── 05-交付物/       ← 最终交付
   ```
4. 更新项目注册表
5. 初始化上下文记忆文件（`00-项目记录/context-memory.md`）
6. 初始化版本记录文件（`00-项目记录/version-log.md`）

**输出**：项目ID + 文件夹路径

**等待 PM 确认**

## 阶段二：背景了解

### 步骤 2.1 — 项目背景描述

- PM 简述项目背景
- AI 倾听并记录，**不急着输出任何文档或分析**
- 仅做简单的理解确认，如：「了解了，这是一个 [一句话概括] 的项目」

**此阶段不做深度分析，只为后续梳理建立基本认知。**

**阶段结束复核**：
- 对照行业规范，检查是否有遗漏的板块（如：用户体系、消息通知、数据统计等）
- 如有遗漏，主动询问 PM：「行业规范中通常包含 [板块名称]，这个项目需要吗？」
- 复核通过后，**等待 PM 确认进入下一阶段**

---

## 阶段三：需求梳理

> 此阶段自动调用 `requirement-analysis` 技能，加载其对话引导策略。

### 步骤 3.1 — 业务流程梳理

- PM 描述大致流程、业务场景
- AI 通过**反复对话**，逐步确认以下内容：
  - 项目端口（iOS / Android / Web / 小程序）
  - 系统角色（用户/管理员/商家等）
  - 完整业务流程（正向/取消/异常路径）
  - 核心业务场景

**对话策略**：
- 每次只聚焦一个主题，不一次性问太多
- PM 描述后，AI 用自己的话复述确认
- 发现矛盾或遗漏时主动追问
- 不确定的内容标注「待验证」

**输出**：业务流程梳理记录（写入 `00-项目记录/`）

**阶段结束复核**：
- 对照行业规范，检查流程梳理是否完整（如：是否遗漏了注册/登录、权限管理等通用流程）
- 如有遗漏，主动询问 PM 是否需要补充
- 复核通过后，**等待 PM 确认流程梳理完整**

**确认后，AI 必须主动询问**：

> 流程梳理已确认。接下来有两种模式：
> - **标准模式**：逐步对话确认功能细节、规则、逻辑 → 写PRD → 审阅 → 生成原型（阶段四~七）
> - **快速通道**：跳过中间对话，AI 根据 [行业] 行业规范自动补齐细节，直接输出你需要的文件。
> 
> 你希望用哪种？如果要快速通道，想直接输出什么？（PRD / 原型 / 全部）

## 快速通道模式

> 阶段三确认后可选。AI 根据行业规范自动补齐细节，跳过阶段四的逐模块对话，直接输出目标文件。

### 触发方式

PM 在阶段三结束后明确选择：
- 「快速通道，直接出PRD」
- 「快速通道，直接出原型」
- 「快速通道，全部输出」
- 「一键生成」

### 自动补齐原则

AI 根据以下规则自动填充未确认的细节：

| 维度 | 填入规则 |
|------|---------|
| 功能模块 | 按行业标准模块清单补齐（详见 `references/industry-rules.md` 对应行业章节） |
| 业务规则 | 按行业通用惯例（如：电商→30分钟未支付自动取消） |
| 数据逻辑 | 按常识推导（如：支付后生成订单号，格式 YYYYMMDD+随机数） |
| 权限控制 | 按角色默认权限（如：普通用户只能看自己的订单） |
| 异常处理 | 按行业标准处理（如：网络异常→提示重试，超时→自动回滚） |
| 页面框架 | 按行业标准布局模板 + 数据类型匹配排版模式 |
| 交互链路 | 按页面层级默认跳转关系 |

### 标注规则

自动补齐的内容使用以下标注：
- `[AI补齐-行业惯例]`：基于行业普遍做法的决策
- `[AI补齐-常识推导]`：基于因果逻辑的推导
- `[AI补齐-默认值]`：选择了行业最常用方案

### 执行流程

#### 快速通道 → 直出 PRD

1. 加载行业自动补齐规则
2. AI 自动完成功能模块拆分 + 规则填充（内部执行，不对话）
3. 输出「自动补齐方案摘要」供 PM 快速审阅（模块清单+关键规则+待确认项）
4. PM 确认或提出修改 → 修改后输出最终 PRD

#### 快速通道 → 直出原型

1. 加载行业自动补齐规则
2. AI 自动完成：模块拆分 → 规则填充 → 页面框架设计（内部执行，不对话）
3. 输出「自动补齐方案摘要」+ 「页面框架设计」供 PM 快速审阅
4. PM 确认后，直接生成 HTML 原型（跳过逐级确认，但保留逐级闭环生成）
5. 生成后执行全量自检清单 + 交付

#### 快速通道 → 全部输出

1-3 同上
4. 先输出 PRD
5. 再生成 HTML 原型
6. 两次输出均需 PM 审阅确认

### 快速通道的边界

**以下情况 AI 必须暂停并询问 PM（不能自动补齐）**：
- 行业规范中存在 2+ 种同样常见的做法，无法确定选哪个
- PM 在阶段一~三中明确表达过特殊偏好
- 涉及合规/法律风险的决策（如金融产品条款、隐私授权范围）
- 项目核心差异化功能（非行业通用功能）

**以下情况直接采用行业最常见方案，不询问**：
- 支付超时时间、退款流程、评价机制等运营规则
- 列表排序规则、搜索逻辑、分页数量等交互细节
- 通知推送时机、消息提醒方式等触达策略
- 页面框架布局、组件排列方式等 UI 结构

### 快速通道质量保障

快速通道产出物必须通过和标准模式同等严格的自检清单：
- PRD：六部分结构 + 自检5项 + 质检6项
- 原型：全链路校验 + HTML自检清单 + 交付标准全部检查项
- 不合格 → 自动修复后再提交 PM

---

## 阶段四：功能细化

> 此阶段继续调用 `requirement-analysis` 技能。

### 步骤 4.1 — 功能模块整理

- 基于已确认的业务流程，整理功能板块
- 通过**反复对话**确认每个模块的细节：
  - 业务规则（校验规则、约束条件、边界情况）
  - 数据逻辑（数据来源、计算方式、存储方式）
  - 权限控制（谁可以操作、权限边界）
  - 关联关系（模块间的依赖和交互）
  - 异常处理（出错时的应对策略）

**对话策略**：
- 逐模块确认，不跳过
- 不确定时给出 2-3 个方案（含优缺点和推荐度）
- 标注 [待PM确认] 和 [MVP]

**输出**：功能模块清单 + 优先级 + 详细规则（写入 `00-项目记录/`）

**阶段结束复核**：
- 对照行业规范，检查功能模块是否有遗漏（如：设置、帮助中心、关于我们等通用模块）
- 如有遗漏，主动询问 PM 是否需要补充
- 检查每个模块的规则是否符合行业标准和合规要求
- 复核通过后，**等待 PM 确认所有功能模块细节**

---

## 阶段五：PRD 文档产出

> 功能确认完毕后，才开始撰写 PRD。

### 步骤 5.1 — 文档格式确认

询问 PM 输出格式：
1. 标准 PRD
2. Markdown
3. HTML

默认：标准 PRD

### 步骤 5.2 — PRD 撰写

调用子 Agent 撰写 PRD，严格遵循 `references/prd-rules.md` 中的规范。

PRD 六部分结构：
1. 文档元信息（名称、项目ID、日期、版本号、状态）
2. 项目概述（背景、建设目标、目标用户、项目边界）
3. 核心业务流程（基于阶段三的梳理结果）
4. 功能模块详细说明（基于阶段四的细化结果）
5. 原型设计方案（端口描述→导航架构→页面优先级→状态矩阵→交互流程→交互行为映射→页面呈现方式→交互规范总则）
6. 待确认清单（所有 [待PM确认] 项汇总）

**输出**：完整 PRD 文档，保存到 `01-需求文档/`

### 步骤 5.3 — 自检

检查项：
- [ ] 是否符合 PRD 六部分结构
- [ ] 是否包含信息架构但不包含视觉描述
- [ ] 是否有模糊空间未标注
- [ ] 所有不确定项是否标注 [待PM确认]
- [ ] MVP 项是否标注 [MVP]
- [ ] 是否包含常识性废话（如有则删除）

### 步骤 5.4 — 质检

检查项：
- [ ] 信息架构完整性
- [ ] 业务流程是否覆盖正向/取消/异常路径
- [ ] 模块间关联是否一致
- [ ] 待确认项是否全部汇总
- [ ] 与行业规范对比，PRD 内容是否符合标准（如：电商项目是否包含售后、物流等必要模块）
- [ ] 如有行业规范要求但 PRD 未覆盖的板块，列出清单询问 PM 是否需要补充

### 步骤 5.5 — PM 终审

**等待 PM 确认后，阶段五完成，进入阶段六。**

## 阶段六：原型生成

> 原型输出为**单个 HTML 文件**，可直接在浏览器中预览，方便通过链接或文件分享给他人。所有样式、交互逻辑内嵌，不依赖外部资源。
>
> **此阶段必须严格遵循 `references/prototype-rules.md` 中以下关键规范**：
> - 功能拆分与合并判断原则（公共/隐私分离、主次分明）
> - 导航架构设计原则（用户视角，非系统模块直译）
> - 统一设计 Token（间距/字体/图标/圆角/颜色）
> - 视口与容器约束（phone-frame 自适应视口，z-index 层级规范，强制声明规则）
> - 页面布局设计原则（视觉层次、分区、图文结合）
> - 数据展示排版规范（5种列表模式 + 选择决策树 + 各类型信息规范）
> - HTML 产出物自检清单（5项强制检查）
> - 浏览器兼容性（SVG currentColor、Flex min-height:0）
> - Z-Index 强制声明 + 排查清单

### 步骤 6.1 — 页面风格确认

根据行业类型和项目背景，给出 2-3 个风格方案供 PM 选择：

| 方案内容 | 说明 |
|---------|------|
| 整体风格 | 如：简约商务 / 活力年轻 / 专业严谨 / 温馨亲和 |
| 主色调 | 2-3 个推荐色值及适用理由 |
| 辅助色 | 搭配的辅助色系 |
| 字体风格 | 如：无衬线现代 / 衬线经典 / 圆角友好 |
| 参考案例 | 同行业优秀产品的风格参考 |

**风格需符合行业特性**：
- 商城类：强调商品展示、购买引导，色彩鲜明有促销感
- 信息发布类：强调内容阅读、信息层次，风格简洁清晰
- 企业服务类：强调专业可信，风格稳重克制
- 社交类：强调互动氛围，风格活泼亲和
- 金融类：强调安全可信，风格严谨稳重
- 教育类：强调学习氛围，风格清新友好

**等待 PM 确认风格方案**

### 步骤 6.2 — 导航架构确认

在梳理页面结构之前，先确认导航架构：

1. **底部导航 TAB**：按用户视角命名（如：首页/发现/消息/我的），非系统模块名
2. **首页金刚区**：承载核心业务入口（8-10个，按使用频率筛选）
3. **我的页面菜单**：承载次要功能和设置

**导航设计原则**（详见 `references/prototype-rules.md`）：
- 底部导航从用户的使用视角出发，不是后台模块列表
- 业务模块入口放在首页金刚区，不放在底部导航
- 次要功能放在「我的」页面列表菜单中

**等待 PM 确认导航架构**

### 步骤 6.3 — 页面结构梳理

在生成任何页面之前，先梳理完整的页面结构：

1. **页面树**：列出所有页面的层级关系
   ```
   登录/注册
   └── 底部导航主页
       ├── Tab1: 首页
       │   ├── 二级页A
       │   │   └── 三级页A1
       │   └── 二级页B
       ├── Tab2: 分类
       │   └── 二级页C
       ├── Tab3: 消息
       └── Tab4: 我的
           ├── 二级页D
           └── 二级页E
   ```

2. **页面清单**：每个页面标注优先级（P0/P1/P2/P3）、页面类型、核心内容

3. **交互关系图**：页面间的跳转关系

**等待 PM 确认页面结构**

### 步骤 6.4 — 页面框架设计 🔑

> **关键步骤**：在生成任何页面代码之前，必须先完成页面框架设计并获 PM 确认。
> 此步骤结合行业规范和项目需求，为每个核心页面设计布局框架和交互方案，确保页面结构合理、交互流畅。

#### 6.4.1 逐页设计框架

对每个 P0/P1 页面，依次输出以下内容：

**单个页面框架设计模板**：

```
## [页面名称]
- 页面类型：[首页/列表/详情/表单/个人中心/...]
- 所属层级：[第一级入口/第二级/第三级]
- 行业参照：[电商/社区/工具/...] — 该页面参照的行业布局标准

### 布局框架（ASCII图）
┌──────────────────────┐
│   顶部区域（导航/搜索） │
├──────────────────────┤
│   核心区域             │
│   （标注组件类型和内容） │
├──────────────────────┤
│   辅助区域             │
├──────────────────────┤
```

### 步骤 6.6 — 逐级闭环生成

按页面层级逐级生成，**每级生成后必须形成完整交互闭环**：

#### 第一级：入口页面
- 登录/注册页（如需要）
- 启动页/引导页（如需要）
- **闭环要求**：登录成功后能跳转到主导航页

#### 第二级：主导航页面
- 底部导航各 TAB 主页面
- **闭环要求**：
  - 各 TAB 之间可以正确切换
  - 每个 TAB 页的入口链接可点击
  - 尚未生成的二级页面点击后显示 Toast 提示：「页面正在建设中，即将上线」
  - 形成一个小闭环，让人知道交互是有效的

#### 第三级：二级页面
- 从主导航进入的各二级页面
- **闭环要求**：
  - 从主导航可以正确跳转到二级页
  - 二级页有返回按钮可回到主导航
  - 二级页内的操作链接可点击（有内容则跳转，无内容则 Toast 提示）

#### 第四级：三级页面
- 从二级页面进入的更深层页面
- **闭环要求**：同上，返回路径完整，交互有效

**生成优先级**：每级内按 P0 → P1 → P2 → P3 顺序

**交互闭环规则**：
- 已生成的页面：正确跳转
- 未生成的页面：Toast 占位提示「页面正在建设中，即将上线」
- 每级生成后，已生成的所有页面之间必须形成完整交互闭环
- 不允许出现死链（点击无反应）

**每级生成后强制执行 HTML 自检清单**（详见 `references/prototype-rules.md`）：
1. 脚本完整性（JS 在 `<script>` 内）
2. 无重复块
3. 核心函数唯一
4. DOM 完整性
5. 实机预览验证

每个项目维护一个 `00-项目记录/context-memory.md`，结构如下：

5. **PM 可随时查看**：「查看当前记忆」→ AI 读取并展示记忆文件内容

- 项目基本信息（ID、名称、端口、角色）

## 版本回溯机制

### 版本记录文件

每个项目维护一个 `00-项目记录/version-log.md`，结构如下：

```markdown
# 版本记录

## v1.0 - [日期时间]
- 阶段: 需求梳理
- 变更: 初始版本
- 文件: 00-项目记录/流程梳理-v1.0.md

## v1.1 - [日期时间]
- 阶段: 需求梳理
- 变更: 补充异常路径
- 文件: 00-项目记录/流程梳理-v1.1.md

## v2.0 - [日期时间]
- 阶段: PRD
- 变更: 初始PRD
- 文件: 01-需求文档/PRD-v2.0.md
```

### 版本保存规则

1. **每个阶段产出物保存为独立文件**，文件名包含版本号
2. **每次重大修改后**，创建新版本，旧版本保留
3. **版本号规则**：
   - 主版本号（v1.0, v2.0）：阶段切换时递增
   - 次版本号（v1.1, v1.2）：同一阶段内重大修改时递增

### 回溯操作

当 PM 说「回溯到 [版本号]」或「回到之前的版本」时：

1. AI 读取版本记录文件，找到对应版本
2. 加载该版本的产出物
3. 从该版本继续工作
4. 新版本号接续（如从 v2.0 回溯到 v1.2，新版本为 v1.3）

### 回溯触发场景

- PM 对当前产出不满意，希望回到之前某个状态
- 发现当前方向偏离了已确认的需求
- 需要对比不同版本的差异

## 确认信号

以下信号视为 PM 确认，可进入下一步：
- 「确认」
- 「可以」
- 「没问题」
- 「继续」
- 「下一步」

PM 未确认前不得推进。

## 多方案决策

不确定时给出 2-3 个方案（含优缺点和推荐度），等 PM 选择。
PM 未选择前不得推进。
PM 也不确定时：选行业最常用方案 + 选实现成本最低方案 + 以 MVP 为第一优先级，标注 [MVP]。

## 行业规范

不确定时主动反问，PM 也不确定时选最常用方案标注 [MVP]：

| 行业 | 必要模块/规范 |
|------|-------------|
| 电商 | 交易履约、售后责任、优惠叠加、物流追踪、评价体系 |
| 内容社区 | UGC 审核、推荐伦理、举报机制、内容分级 |
| 企业服务 | 多租户隔离、RBAC 权限、操作审计、数据备份 |
| 金融 | PCI DSS、资金流一致性、风控规则、合规披露 |
| 教育 | 课程体系、学习进度、证书发放、互动答疑 |
| 医疗健康 | 数据隐私（HIPAA等）、处方合规、问诊流程 |
| 社交 | 好友体系、消息推送、隐私设置、举报封禁 |
| O2O/本地生活 | 商家入驻、服务履约、评价退款、定位服务 |

**行业规范反问机制**：
- 每个阶段结束时，对照上表检查当前项目是否有遗漏的必要模块
- 发现遗漏时主动询问：「[行业] 项目通常需要包含 [模块]，当前方案中未涉及，这个项目需要吗？」
- PM 确认不需要则标注 [已排除]，确认需要则补充到方案中
