# Prototype Workflow

从需求到原型的完整工作流，分七阶段执行。PRD 文档是原型的唯一输入源。

## 核心原则

1. **PM 驱动**：任何环节 PM 未确认，禁止进入下一步。AI 不替 PM 做决定。
2. **主 Agent 只决策审核，不动手**：文档、原型全部由子 Agent 产出。
3. **先理解再动手**：收到需求先复述、做完整性检查、评估新鲜度，PM 确认后才开始。
4. **防幻觉**：标注置信度（确定/推测/未知），不编造数据。
5. **断点续传**：每次确认写记录到 `00-项目记录/`，上下文断了可无缝恢复。
6. **MVP 优先**：首次交付以跑通核心路径为目标，边缘内容标注 [MVP]。
7. **每步复核质检**：每个阶段/步骤结束后，必须复核产出物是否符合行业规范和标准，发现偏差立即修正。
8. **行业规范反问**：对照行业规范检查是否有遗漏板块，如有则主动询问 PM 该项目是否需要。
9. **输出格式确认**：任何文件输出前，必须先询问 PM 需要的格式（标准PRD/Markdown/HTML/其他）。
10. **输出合规**：所有产出物必须符合对应行业规范和标准。
11. **逐级闭环生成**：页面按层级逐级生成（登录→主导航→二级→三级），每级生成后必须形成完整交互闭环。
12. **先结构后页面**：设计时先梳理页面结构（页面树/层级关系），确认后再生成页面。
13. **项目经验沉淀**：每次项目结束后，整理本次项目的规范性要求，形成技能表。如有需要可补充到技能库中，行业特性类需写明适用行业和调用节点。
14. **上下文记忆**：自动整理并记忆项目过程中的所有关键要点，后续生成过程中持续引用，不遗忘已确认的内容。
15. **版本回溯**：每个阶段产出物保存版本记录，如出现问题可回溯到之前任意版本。
16. **端口规范优先**：设计时必须考虑项目端口特性（小程序/iOS/Android/Web/H5），各端口有独立的系统规范和限制（如小程序胶囊按钮区禁止放置内容），禁止用单一端口的设计套用到所有端口。
17. **结构性调整原则**：当板块或功能位置需要调整时，必须从用户需求和场景出发找最合适的位置，禁止以"最小改动"为目标做折中调整。如果合理调整会引发较大变动，说明原设计存在更大问题，应接受大变动并重新设计，而非妥协。

## 触发条件

- PM 声明"新项目"
- 用户需要制作原型
- 用户需要编写 PRD
- 用户从需求出发进行产品设计
- 用户提到"原型""PRD""需求文档""产品设计"等关键词

## 引用规则

执行过程中，根据当前阶段加载对应规则文件：

- **阶段二（背景了解）**：加载 `references/ai-assessment-template.md`（AI化可能性评估）
- **阶段三（需求梳理）**：加载 `references/question-list-template.md`（待确认问题清单模板）+ 自动调用 `requirement-analysis` 技能（对话引导策略）
- **阶段四（功能细化）**：自动调用 `requirement-analysis` 技能
- **阶段五（PRD 产出）**：加载 `references/prd-rules.md`
- **阶段六（原型生成）**：
  - 加载 `references/prototype-rules.md`（全行业通用规范，含规则编号体系/设计纲要规范/交互补全清单/质量评分标准）
  - 加载 `references/industry-rules.md`（行业特定规范）
  - 加载 `references/industry-templates.md`（行业模板库）
  - 加载 `references/component-library.md`（组件库）
  - 加载 `references/design-patterns.md`（设计模式库）
  - 加载 `references/case-library.md`（案例库沉淀机制）
  - 加载 `references/design-outline-template.md`（设计纲要模板）
  - **调用 `references/ue-designer.md`（老K设计师Agent）主导设计纲要生成和三层审查**
- **全局适用**：加载 `references/priority-rules.md`、`references/project-rules.md`

## 阶段一：项目启动

### 步骤 1.1 — 新项目声明

当 PM 表示"接下来是一个新项目"时：

1. 分配项目ID（P+三位数字，从注册表获取）
2. 创建项目文件夹，命名格式：`P编号-项目简称-年月`
3. 创建标准子目录：
   ```
   P编号-项目简称-年月/
   ├── 00-项目记录/     ← 确认记录、断点续传
   ├── 01-需求文档/     ← PRD 文档
   ├── 04-原型/         ← 原型文件
   └── 05-交付物/       ← 最终交付
   ```
4. 更新项目注册表
5. 初始化上下文记忆文件（`00-项目记录/context-memory.md`）
6. 初始化版本记录文件（`00-项目记录/version-log.md`）

**输出**：项目ID + 文件夹路径

**等待 PM 确认**

## 阶段二：背景了解

### 步骤 2.1 — 项目背景描述

- PM 简述项目背景
- AI 倾听并记录，**不急着输出任何文档或分析**
- 仅做简单的理解确认，如：「了解了，这是一个 [一句话概括] 的项目」

**此阶段不做深度分析，只为后续梳理建立基本认知。**

### 步骤 2.2 — 项目级AI适配性快速判断 🔑

> **新增步骤**：在项目背景明确后，进行项目级的AI适配性快速判断，培养PM的AI思考意识。此阶段不做详细评估，只判断"是否值得考虑AI"。

**执行流程**：

1. **AI引导PM思考**（3个问题）：
   - "这个项目要解决的核心问题，是否有重复性、规律性的工作可以被AI替代？"
   - "当前是否有大量历史数据可以供AI学习？"
   - "如果引入AI，您更希望它提升效率（降本）还是提升效果（增效）？"

2. **快速判断**（4项勾选）：

| 判断项 | 是否满足 |
|--------|---------|
| 有大量历史数据可学 | [ ] 是 / [ ] 否 |
| 任务定义明确，专家能轻松判断对错 | [ ] 是 / [ ] 否 |
| 容忍一定程度的错误 | [ ] 是 / [ ] 否 |
| 需要规模化、7x24小时处理 | [ ] 是 / [ ] 否 |

3. **判断结论**：
- 满足≥3项 → **值得考虑AI**，进入阶段三时关注AI化机会，阶段四后做详细评估
- 满足≤2项 → **暂不考虑AI**，按常规项目流程进行

**输出**：《项目级AI适配性判断》（一句话结论，记入 `00-项目记录/context-memory.md`）

**阶段结束复核**：
- 对照行业规范，检查是否有遗漏的板块（如：用户体系、消息通知、数据统计等）
- 如有遗漏，主动询问 PM：「行业规范中通常包含 [板块名称]，这个项目需要吗？」
- 复核通过后，**等待 PM 确认进入下一阶段**

## 阶段三：需求梳理

> 此阶段核心目标：基于PM提供的功能清单，AI整理业务流程，输出待确认问题清单，PM开会确认后AI补充完善。
>
> **关键流程**：功能清单 → AI整理流程 → 输出问题清单 → PM开会确认 → AI补充完善 → 需求细化

### 步骤 3.1 — 接收功能清单

- AI主动询问PM：「请提供初步的功能清单（可以是文档、文字描述或列表形式）」
- **如PM提供了功能清单**：AI接收并逐条理解
- **如PM未提供功能清单**：PM直接描述需求，AI记录并整理成功能清单
- AI复述确认：「我整理的功能清单如下，请确认是否有遗漏或理解错误」

**输出**：确认后的功能清单（写入 `00-项目记录/`）

---

### 步骤 3.2 — AI整理业务流程

- 基于**确认的功能清单** + **阶段二背景**，AI整理业务流程
- 覆盖三种路径：
  - **正向路径**：正常操作流程（主流程）
  - **取消路径**：用户中途取消/撤回的操作
  - **异常路径**：出错、超时、网络异常等处理
- 标注不确定点：
  - `[待确认]`：需要PM/客户确认的内容
  - `[AI假设]`：AI基于常识做的假设，需PM确认
  - `[行业惯例]`：按行业通用做法处理，可后续调整

**输出**：业务流程初稿（写入 `00-项目记录/`）

---

### 步骤 3.3 — 输出待确认问题清单 🔑

> **关键步骤**：AI审查业务流程，主动暴露理解中的问题，让PM带着明确的问题去和客户开会。

**AI识别以下问题类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **模糊点** | 描述不清晰，有多种理解方式 | "快速处理"是指30分钟还是2小时？ |
| **矛盾点** | 功能间逻辑冲突 | A规则说必须实名，B流程说游客可用 |
| **遗漏点** | 缺少必要环节 | 退款流程中缺少"退款失败"的处理 |
| **待决策** | 需要业务方决策的规则 | 优惠券能否叠加使用？ |
| **边界点** | 边界条件不明确 | 商品库存为0时，已加入购物车的如何处理？ |

**识别信号**（出现以下情况必须列为问题）：
1. 功能清单中出现"等"、"快速"、"视情况而定"、"原则上"等模糊词汇
2. 业务流程缺失开始/结束条件、异常处理、权限判断、数据校验
3. 两个功能对同一数据的处理规则矛盾
4. 行业规范要求但未提及（如电商未提及售后/退款）

**输出要求**：
- 严格遵循 `references/question-list-template.md` 模板
- 按优先级排序：高（阻塞流程）/ 中（影响规则）/ 低（细节优化）
- 每个问题包含：问题描述、AI当前理解、影响范围、建议确认方向
- 输出：《待确认问题清单》（写入 `00-项目记录/`）

**PM拿着问题清单与客户开会确认**

---

### 步骤 3.4 — 补充完善业务流程

- PM提供会议结论（按问题编号逐一反馈）
- AI根据会议结论补充完善业务流程

**会议结论类型处理**：

| 结论类型 | AI处理方式 |
|---------|-----------|
| **已确认** | 按确认内容更新业务流程，标记`[已确认]` |
| **待进一步确认** | 保留原问题，补充新发现的问题，输出《待确认问题清单V2》 |
| **客户也未确定** | 标注`[需PM决策]`，给出2-3个方案供PM选择 |

**循环机制**：
- 如产生新问题或高优先级问题未解决 → 回到步骤3.3，输出新版问题清单
- 循环直至无高优先级问题

**输出**：完善的业务流程（写入 `00-项目记录/`）

---

### 步骤 3.5 — 需求确认与场景细化

- 基于**完善的业务流程**，AI与PM确认以下内容：
  - 项目端口（iOS / Android / Web / 小程序）
  - 系统角色（用户/管理员/商家等）
  - 核心业务场景（最典型的3-5个使用场景）
  - 关键业务规则（校验规则、约束条件、边界情况）

**对话策略**：
- 每次只聚焦一个主题，不一次性问太多
- PM描述后，AI用自己的话复述确认
- 发现矛盾或遗漏时主动追问
- 不确定的内容标注 `[待验证]`

**输出**：完整的业务流程梳理记录（写入 `00-项目记录/`）

**阶段结束复核**：
- 对照行业规范，检查流程梳理是否完整（如：是否遗漏了注册/登录、权限管理等通用流程）
- 如有遗漏，主动询问 PM 是否需要补充
- 复核通过后，**等待 PM 确认流程梳理完整**

**确认后，AI 必须主动询问**：

> 流程梳理已确认。接下来有两种模式：
> - **标准模式**：逐步对话确认功能细节、规则、逻辑 → 写PRD → 审阅 → 生成原型（阶段四~七）
> - **快速通道**：跳过中间对话，AI 根据 [行业] 行业规范自动补齐细节，直接输出你需要的文件。
> 
> 你希望用哪种？如果要快速通道，想直接输出什么？（PRD / 原型 / 全部）

## 快速通道模式

> 步骤 3.5 结束后可选。AI 根据行业规范自动补齐细节，跳过阶段四的逐模块对话，直接输出目标文件。
>
> **注意**：若步骤 3.3 输出的问题清单中有高优先级问题未解决，**禁止进入快速通道**，必须先完成问题确认。

### 触发方式

PM 在步骤 3.5 结束后明确选择：
- 「快速通道，直接出PRD」
- 「快速通道，直接出原型」
- 「快速通道，全部输出」
- 「一键生成」

### 自动补齐原则

AI 根据以下规则自动填充未确认的细节：

| 维度 | 填入规则 |
|------|---------|
| 功能模块 | 按行业标准模块清单补齐（详见 `references/industry-rules.md` 对应行业章节） |
| 业务规则 | 按行业通用惯例（如：电商→30分钟未支付自动取消） |
| 数据逻辑 | 按常识推导（如：支付后生成订单号，格式 YYYYMMDD+随机数） |
| 权限控制 | 按角色默认权限（如：普通用户只能看自己的订单） |
| 异常处理 | 按行业标准处理（如：网络异常→提示重试，超时→自动回滚） |
| 页面框架 | 按行业标准布局模板 + 数据类型匹配排版模式 |
| 交互链路 | 按页面层级默认跳转关系 |

### 标注规则

自动补齐的内容使用以下标注：
- `[AI补齐-行业惯例]`：基于行业普遍做法的决策
- `[AI补齐-常识推导]`：基于因果逻辑的推导
- `[AI补齐-默认值]`：选择了行业最常用方案

### 执行流程

#### 快速通道 → 直出 PRD

1. 加载行业自动补齐规则
2. AI 自动完成功能模块拆分 + 规则填充（内部执行，不对话）
3. 输出「自动补齐方案摘要」供 PM 快速审阅（模块清单+关键规则+待确认项）
4. PM 确认或提出修改 → 修改后输出最终 PRD

#### 快速通道 → 直出原型

1. 加载行业自动补齐规则
2. AI 自动完成：模块拆分 → 规则填充 → 页面框架设计（内部执行，不对话）
3. 输出「自动补齐方案摘要」+ 「页面框架设计」供 PM 快速审阅
4. PM 确认后，直接生成 HTML 原型（跳过逐级确认，但保留逐级闭环生成）
5. 生成后执行全量自检清单 + 交付

#### 快速通道 → 全部输出

1-3 同上
4. 先输出 PRD
5. 再生成 HTML 原型
6. 两次输出均需 PM 审阅确认

### 快速通道的边界

**以下情况 AI 必须暂停并询问 PM（不能自动补齐）**：
- 行业规范中存在 2+ 种同样常见的做法，无法确定选哪个
- PM 在阶段一~三（含问题清单确认过程）中明确表达过特殊偏好
- 涉及合规/法律风险的决策（如金融产品条款、隐私授权范围）
- 项目核心差异化功能（非行业通用功能）
- 步骤 3.3 的问题清单中有未解决的高优先级问题

**以下情况直接采用行业最常见方案，不询问**：
- 支付超时时间、退款流程、评价机制等运营规则
- 列表排序规则、搜索逻辑、分页数量等交互细节
- 通知推送时机、消息提醒方式等触达策略
- 页面框架布局、组件排列方式等 UI 结构

### 快速通道质量保障

快速通道产出物必须通过和标准模式同等严格的自检清单：
- PRD：六部分结构 + 自检5项 + 质检6项
- 原型：全链路校验 + HTML自检清单 + 交付标准全部检查项
- 不合格 → 自动修复后再提交 PM

## 阶段四：功能细化

> 此阶段继续调用 `requirement-analysis` 技能。

### 步骤 4.1 — 功能模块整理

- 基于已确认的业务流程，整理功能板块
- 通过**反复对话**确认每个模块的细节：
  - 业务规则（校验规则、约束条件、边界情况）
  - 数据逻辑（数据来源、计算方式、存储方式）
  - 权限控制（谁可以操作、权限边界）
  - 关联关系（模块间的依赖和交互）
  - 异常处理（出错时的应对策略）

**对话策略**：
- 逐模块确认，不跳过
- 不确定时给出 2-3 个方案（含优缺点和推荐度）
- 标注 [待PM确认] 和 [MVP]

**输出**：功能模块清单 + 优先级 + 详细规则（写入 `00-项目记录/`）

**阶段结束复核**：
- 对照行业规范，检查功能模块是否有遗漏（如：设置、帮助中心、关于我们等通用模块）
- 如有遗漏，主动询问 PM 是否需要补充
- 检查每个模块的规则是否符合行业标准和合规要求
- 复核通过后，**等待 PM 确认所有功能模块细节**

### 步骤 4.2 — AI功能单元拆解与详细评估 🔑

> **新增步骤**：功能模块确认后，对涉及AI的功能进行单元级详细评估。此时业务流程已清晰，拆解更准确。

**前置条件**：阶段二判断为"值得考虑AI"的项目才执行此步骤。若阶段二判断为"暂不考虑AI"，跳过此步骤。

**执行流程**：

#### 第一步：拆解AI功能单元

基于已确认的功能模块，AI引导PM拆解AI功能单元。

**引导问题**：
- "在已确认的功能模块中，哪些环节可以被AI替代或增强？"
- "每个AI环节是否有明确的输入数据和期望输出？"
- "请把AI相关功能拆成几个'最小AI功能单元'"

**拆解原则**：
- 每个单元对应一个完整的"输入→处理→输出"闭环
- 单元之间尽量独立，减少耦合
- 颗粒度适中：既不过大（难以评估），也不过小（价值不明显）

**拆解示例**：
- 智能客服系统 → 单元1：意图识别 / 单元2：回复生成 / 单元3：情绪识别
- 商品推荐系统 → 单元1：用户画像 / 单元2：推荐排序

**输出**：AI功能单元清单

#### 第二步：逐单元详细评估

对每个AI功能单元，AI填写《AI化可能性评估》，严格遵循 `references/ai-assessment-template.md` 模板。

**7个评估维度**：
1. 问题定义与AI适配性判断（4项勾选）
2. AI任务类型判断（分类/回归/聚类/生成/排序）
3. 数据可行性快速自查
4. 核心技术指标优先级定义
5. 失败场景与容错成本预估
6. 价值与成本粗略估算
7. 综合评估结论

**多单元汇总**：

| 序号 | AI功能单元 | 适配性 | 综合建议 | 优先级 |
|------|-----------|--------|---------|--------|
| 1 | | | | |

**项目级AI策略**：
- **全部建议尝试**：项目整体适合AI化，按优先级逐个实施
- **部分建议尝试**：优先实施高适配性单元，低适配性单元寻找替代方案
- **全部不建议**：项目暂不适合AI化，按常规项目流程进行

**输出**：
- 每个功能单元独立评估
- 多单元汇总评估表
- 保存到 `00-项目记录/ai-assessment/`

**评估后处理**：
- 高适配性单元：在PRD中明确AI功能需求
- 低适配性单元：在PRD中标注为常规功能或[MVP]

### 【第二层】步骤 6.6 — 逐级闭环生成 + 交互补全

按页面层级逐级生成，**每级生成后必须形成完整交互闭环**。

#### 6.6.1 生成优先级

**第一级：入口页面**
- 登录/注册页（如需要）
- 启动页/引导页（如需要）
- **闭环要求**：登录成功后能跳转到主导航页

**第二级：主导航页面**
- 底部导航各 TAB 主页面
- **闭环要求**：各 TAB 之间可以正确切换，每个 TAB 页的入口链接可点击

**第三级：二级页面**
- 从主导航进入的各二级页面
- **闭环要求**：从主导航可以正确跳转到二级页，二级页有返回按钮

**第四级：三级页面**
- 从二级页面进入的更深层页面
- **闭环要求**：返回路径完整，交互有效

每级内按 P0 → P1 → P2 → P3 顺序生成。

#### 6.6.2 交互补全机制（强制）

**每个页面生成时，必须对照"交互补全清单"逐项检查，缺失的必须补充。**

详见 `references/prototype-rules.md` 交互补全清单章节，包含14项必检交互：
- 页面跳转、返回路径、中部弹窗、底部弹窗、ActionSheet、Toast反馈
- 加载状态、空状态、错误状态、下拉刷新、上拉加载、左滑操作
- 搜索功能、筛选排序

**交互补全原则**：设计纲要中规划的交互组件必须实现，未规划的交互组件如发现缺失也必须补充。

#### 6.6.3 每级生成后自检

**HTML 产出物自检清单**（8项）：
1. 脚本完整性（JS 在 `<script>` 内）
2. 无重复块
3. 核心函数唯一
4. DOM 完整性
5. Design Token 合规（图标/图片/间距/字体尺寸）
6. SVG 与文字容器规范
7. 滚动条隐藏
8. 实机预览验证（浏览器打开确认无白屏/乱码/报错/布局失调）

**自动截图检查**：
1. 启动本地HTTP服务器预览原型
2. 使用浏览器工具截取各页面截图
3. 对照检查清单逐项核对截图：
   - 布局比例是否协调（图标/图片/文字大小）
   - 是否与行业参照APP布局模式一致
   - 有无明显视觉异常（元素重叠/错位/溢出）
4. 发现问题立即修复，不交付PM预览

### 【第三层】步骤 6.7 — 质量评分

**规则：生成后不直接交付PM，先进行"质量评分"，低于80分自动修复。**

#### 6.7.1 质量评分标准

详见 `references/prototype-rules.md` 「质量评分标准」章节，包含5个评分维度（设计感25分/交互完整性25分/行业符合度20分/功能完整性20分/代码质量10分）及详细扣分项。

#### 6.7.2 评分规则

- 90-100分：优秀，直接交付PM
- 80-89分：良好，交付PM
- 70-79分：及格，自动修复后重新评分
- 60-69分：不及格，返回检查设计纲要
- <60分：严重问题，重新生成

### 【第三层】步骤 6.10 — 老K审查节点③：交付前走查

所有页面生成完毕、质量评分通过后，老K进行最终交付前走查：

**走查维度**：
1. **设计还原度** — 生成的页面是否还原了设计纲要中的设计意图
2. **交互细腻度** — 动画、过渡、反馈是否自然流畅
3. **视觉精致度** — 细节处理（圆角、阴影、间距、对齐）是否到位
4. **异常处理** — 空状态、错误态、加载态是否设计得体
5. **跨页面一致性** — 相同组件在不同页面表现是否一致

```
|------|------|---------|---------|---------|
| 1 | 首页 | xxx | 高/中/低 | xxx |

### 修复后确认
[如走查不通过，修复后老K重新走查确认]
```

项目结束后，整理本次项目的规范性要求：

     - 具体规范内容

### 步骤 7.2 — AI经验沉淀（如项目涉及AI）

> 若本项目经过AI化评估或实施了AI功能，额外沉淀AI相关经验。

**沉淀内容**：

1. **AI功能单元回顾**：
   - 哪些AI功能单元实际实施了？效果如何？
   - 哪些AI功能单元评估通过但未实施？原因是什么？
   - 哪些AI功能单元评估未通过？是否有新的数据/技术使其变得可行？

2. **数据经验**：
   - 实际使用的数据来源、质量、量级
   - 数据预处理的经验（清洗、标注、增强）
   - 数据获取的难点和解决方案

3. **模型/算法经验**：
   - 实际采用的AI方案（调用API/微调/自研）
   - 模型表现与预期的差距
   - 调优经验和关键参数

4. **上线经验**：
   - 实际出错场景与兜底方案的有效性
   - 用户反馈和接受度
   - 性能表现（响应时间、并发能力）

5. **成本复盘**：
   - 实际投入 vs 预估成本
   - 实际收益 vs 预估价值
   - ROI总结

**输出**：《AI经验沉淀报告》（写入 `00-项目记录/ai-assessment/ai-retrospective.md`）

**询问 PM**：是否将本次AI经验补充到 `references/ai-assessment-template.md` 的示例库中，供后续项目参考

## 版本回溯机制

### 版本记录文件

每个项目维护一个 `00-项目记录/version-log.md`，结构如下：

```markdown
# 版本记录

## v1.0 - [日期时间]
- 阶段: 需求梳理
- 变更: 初始版本
- 文件: 00-项目记录/流程梳理-v1.0.md

## v1.1 - [日期时间]
- 阶段: 需求梳理
- 变更: 补充异常路径
- 文件: 00-项目记录/流程梳理-v1.1.md

## v2.0 - [日期时间]
- 阶段: PRD
- 变更: 初始PRD
- 文件: 01-需求文档/PRD-v2.0.md
```

### 版本保存规则

1. **每个阶段产出物保存为独立文件**，文件名包含版本号
2. **每次重大修改后**，创建新版本，旧版本保留
3. **版本号规则**：
   - 主版本号（v1.0, v2.0）：阶段切换时递增
   - 次版本号（v1.1, v1.2）：同一阶段内重大修改时递增

### 回溯操作

当 PM 说「回溯到 [版本号]」或「回到之前的版本」时：

1. AI 读取版本记录文件，找到对应版本
2. 加载该版本的产出物
3. 从该版本继续工作
4. 新版本号接续（如从 v2.0 回溯到 v1.2，新版本为 v1.3）

### 回溯触发场景

- PM 对当前产出不满意，希望回到之前某个状态
- 发现当前方向偏离了已确认的需求
- 需要对比不同版本的差异

## 确认信号

以下信号视为 PM 确认，可进入下一步：
- 「确认」
- 「可以」
- 「没问题」
- 「继续」
- 「下一步」

PM 未确认前不得推进。

## 多方案决策

不确定时给出 2-3 个方案（含优缺点和推荐度），等 PM 选择。
PM 未选择前不得推进。
PM 也不确定时：选行业最常用方案 + 选实现成本最低方案 + 以 MVP 为第一优先级，标注 [MVP]。

## 行业规范

不确定时主动反问，PM 也不确定时选最常用方案标注 [MVP]：

| 行业 | 必要模块/规范 |
|------|-------------|
| 电商 | 交易履约、售后责任、优惠叠加、物流追踪、评价体系 |
| 内容社区 | UGC 审核、推荐伦理、举报机制、内容分级 |
| 企业服务 | 多租户隔离、RBAC 权限、操作审计、数据备份 |
| 金融 | PCI DSS、资金流一致性、风控规则、合规披露 |
| 教育 | 课程体系、学习进度、证书发放、互动答疑 |
| 医疗健康 | 数据隐私（HIPAA等）、处方合规、问诊流程 |
| 社交 | 好友体系、消息推送、隐私设置、举报封禁 |
| O2O/本地生活 | 商家入驻、服务履约、评价退款、定位服务 |

**行业规范反问机制**：
- 每个阶段结束时，对照上表检查当前项目是否有遗漏的必要模块
- 发现遗漏时主动询问：「[行业] 项目通常需要包含 [模块]，当前方案中未涉及，这个项目需要吗？」
- PM 确认不需要则标注 [已排除]，确认需要则补充到方案中
