# Prototype Workflow

从需求到原型的完整工作流，分七阶段执行。PRD 文档是原型的唯一输入源。

## 核心原则

1. **PM 驱动**：任何环节 PM 未确认，禁止进入下一步。AI 不替 PM 做决定。
2. **主 Agent 只决策审核，不动手**：文档、原型全部由子 Agent 产出。
3. **先理解再动手**：收到需求先复述、做完整性检查、评估新鲜度，PM 确认后才开始。
4. **防幻觉**：标注置信度（确定/推测/未知），不编造数据。
5. **断点续传**：每次确认写记录到 `00-项目记录/`，上下文断了可无缝恢复。
6. **MVP 优先**：首次交付以跑通核心路径为目标，边缘内容标注 [MVP]。
7. **每步复核质检**：每个阶段/步骤结束后，必须复核产出物是否符合行业规范和标准，发现偏差立即修正。
8. **行业规范反问**：对照行业规范检查是否有遗漏板块，如有则主动询问 PM 该项目是否需要。
9. **输出格式确认**：任何文件输出前，必须先询问 PM 需要的格式（标准PRD/Markdown/HTML/其他）。
10. **输出合规**：所有产出物必须符合对应行业规范和标准。
11. **逐级闭环生成**：页面按层级逐级生成（登录→主导航→二级→三级），每级生成后必须形成完整交互闭环。
12. **先结构后页面**：设计时先梳理页面结构（页面树/层级关系），确认后再生成页面。
13. **项目经验沉淀**：每次项目结束后，整理本次项目的规范性要求，形成技能表。如有需要可补充到技能库中，行业特性类需写明适用行业和调用节点。
14. **上下文记忆**：自动整理并记忆项目过程中的所有关键要点，后续生成过程中持续引用，不遗忘已确认的内容。
15. **版本回溯**：每个阶段产出物保存版本记录，如出现问题可回溯到之前任意版本。
16. **端口规范优先**：设计时必须考虑项目端口特性（小程序/iOS/Android/Web/H5），各端口有独立的系统规范和限制（如小程序胶囊按钮区禁止放置内容），禁止用单一端口的设计套用到所有端口。
17. **结构性调整原则**：当板块或功能位置需要调整时，必须从用户需求和场景出发找最合适的位置，禁止以"最小改动"为目标做折中调整。如果合理调整会引发较大变动，说明原设计存在更大问题，应接受大变动并重新设计，而非妥协。
18. **督查全程跟随**：每次行动前后自动调用督查Agent（`references/supervisor.md`）进行预防检查和复盘检查。发现违规立即中断并报告PM，PM裁决修正/豁免/跳过后方可继续。
19. **意图不清不行动**：当PM回复模糊、未直接回应问题、或可被多种方式理解时，AI必须停止当前操作，向PM澄清意图，禁止盲目猜测和行动。防幻觉、防臆想是贯穿全流程的底线要求。

## 意图确认机制

> **目的**：解决"PM回复不明确时AI胡乱猜测、擅自行动"的问题。确保AI在弄清问题、明确意图之前绝不盲目动手。
> **适用范围**：主调度器AI、所有子Agent（设计师/设计分析师/验收员/督查）。

### 无效信号清单（一律视为未确认）

| 信号类型 | 示例 | AI正确处理 |
|---------|------|-----------|
| 模糊回应 | "好的""嗯""行""知道了""先这样吧" | 视为未确认，追问："请确认我的理解是否正确..." |
| 转移话题 | 不回答当前问题，说别的事 | 视为未确认，拉回："关于刚才的XX问题，您还没确认..." |
| 提出新问题 | "那XX怎么办" | 视为未确认，先处理原问题："我们先确认当前问题，再讨论XX" |
| 沉默/无回复 | | 等待回复，不自动推进，不猜测 |
| 部分回应 | 只回答了多问题中的一个 | 视为未确认，追问其余问题 |
| 情绪性回应 | "随便""都行""你看着办" | 视为未确认，给出2-3个方案请PM选择 |
| 反问/质疑 | "为什么要这样做" | 视为未确认，先解释再重新请求确认 |

### 有效确认信号（必须同时满足）

1. PM明确使用了确认词汇：**确认、可以、没问题、继续、下一步、通过、就这样**
2. PM的回复**直接回应了AI当前提出的问题/方案**
3. PM的回复**没有歧义**，只有一种合理解读

### 行动前意图检查三问

AI每次准备行动前，必须自检：

**第一问：我理解了什么？**
- 用自己的话复述对PM意图的理解
- 如果理解有多种可能，列出所有可能的理解，请PM选择

**第二问：PM确认了吗？**
- 检查PM的上一条回复是否属于"有效确认信号"
- 如PM回复属于"无效信号清单"中的任意一项 → 停止行动，重新澄清

**第三问：我的理解有歧义吗？**
- 是否存在多种执行方式？
- 如有歧义，给出2-3个方案供PM选择，标注推荐和理由
- **禁止在歧义未消除前擅自选择方案执行**

### 模糊回复处理流程

```
PM回复模糊/不明确
  ↓
AI停止当前所有操作
  ↓
AI向PM输出《意图澄清请求》：
  - 我的当前理解是：...
  - 但我发现您的回复可能存在以下理解方式：
    A. ...
    B. ...
    C. ...
  - 请确认是哪种，或补充说明您的意图
  ↓
等待PM明确回复
  ↓
PM回复明确 → 继续执行
PM仍模糊 → 再次澄清（最多3轮）
```

### 修改方案确认流程

用户明确要求"每次修改方案要求确认"。执行规则如下：

1. **生成方案后必须等待确认**
   - AI输出修改方案概要（修改内容 + 修改原因 + 预期效果）
   - 明确询问PM："以上方案是否确认？确认后我将执行修改"
   - **未获得PM明确确认前，禁止执行任何修改操作**

2. **方案概要格式**
   ```
   ## 修改方案概要
   
   | 序号 | 修改位置 | 修改内容 | 修改原因 | 预期效果 |
   |------|---------|---------|---------|---------|
   | 1 | ... | ... | ... | ... |
   
   **请确认以上方案后，我将执行修改。**
   ```

3. **紧急修复例外**
   - P0阻断性错误（如登录无法使用、页面白屏）可先行修复
   - 修复后必须向PM报告："发现P0问题[XX]，已紧急修复，详情如下..."

## 触发条件

### 主流程触发

- PM 声明"新项目"
- 用户需要制作原型
- 用户需要编写 PRD
- 用户从需求出发进行产品设计
- 用户提到"原型""PRD""需求文档""产品设计"等关键词

### 设计分析师独立触发

- 用户说"分析这个页面/原型"
- 用户说"提炼这个页面的设计规则"
- 用户说"看看这个设计有什么值得学的"
- 用户说"把这个页面的规则存下来"
- 用户提供页面链接/截图/HTML代码并要求分析设计

> 独立触发时，直接调用 `references/design-analyst.md` 中的设计分析师Agent，输出提炼的规则供PM审核，审核通过后追加到 `references/frontend-design-rules.md`。

### GitHub推送独立触发

- 用户说"推送GitHub"
- 用户说"推送技能"
- 用户说"提交代码"
- 用户说"同步到GitHub"
- 步骤7.3或7.4完成后用户确认推送

> 独立触发时，直接执行GitHub推送流程（见阶段七后「GitHub推送流程」章节）。推送前检查Git状态，推送后报告结果。

## 引用规则

执行过程中，根据当前阶段加载对应规则文件：

- **阶段二（背景了解）**：加载 `references/ai-assessment-template.md`（AI化可能性评估）
- **阶段三（需求梳理）**：加载 `references/question-list-template.md`（待确认问题清单模板）+ 自动调用 `requirement-analysis` 技能（对话引导策略）
- **阶段四（功能细化）**：自动调用 `requirement-analysis` 技能
- **阶段五（PRD 产出）**：加载 `references/prd-rules.md`
- **阶段六（原型生成）**：
  - 加载 `references/prototype-rules.md`（全行业通用规范，含规则编号体系/设计纲要规范/交互补全清单/质量评分标准）
  - 加载 `references/frontend-design-rules.md`（案例驱动设计规则，从页面提炼的具体规则，最高优先级）
  - 加载 `references/user-centric-design.md`（用户群体差异化设计指南，多端口设计分化参考）
  - 加载 `references/industry-rules.md`（行业特定规范）
  - 加载 `references/industry-templates.md`（行业模板库）
  - 加载 `references/component-library.md`（组件库）
  - 加载 `references/design-patterns.md`（设计模式库）
  - 加载 `references/case-library.md`（案例库沉淀机制）
  - 加载 `references/design-outline-template.md`（设计纲要模板）
  - **调用 `references/designer.md`（设计师Agent）主导设计纲要生成、三层审查和反馈判定**
  - **调用 `references/design-analyst.md`（设计分析师Agent）在设计纲要和框架设计后审查、项目收尾时提炼规则**
  - **调用 `references/inspector.md`（验收员Agent）在原型生成后从用户视角测试**
- **全局适用**：加载 `references/priority-rules.md`、`references/project-rules.md`
- **流程监督**：全程调用 `references/supervisor.md`（督查Agent），在每次行动前后自动执行预防检查和复盘检查，确保不跳步骤、不遗漏Agent、不违反规范

## 阶段一：项目启动

> **[督查-预防]** 检查是否有进行中的项目、PM是否声明了新项目

### 步骤 1.1 — 新项目声明

当 PM 表示"接下来是一个新项目"时：

1. 分配项目ID（P+三位数字，从注册表获取）
2. 创建项目文件夹，命名格式：`P编号-项目简称-年月`
3. 创建标准子目录：
   ```
   P编号-项目简称-年月/
   ├── 00-项目记录/     ← 确认记录、断点续传
   ├── 01-需求文档/     ← PRD 文档
   ├── 04-原型/         ← 原型文件
   └── 05-交付物/       ← 最终交付
   ```
4. 更新项目注册表
5. 初始化上下文记忆文件（`00-项目记录/context-memory.md`）
6. 初始化版本记录文件（`00-项目记录/version-log.md`）

**输出**：项目ID + 文件夹路径

**等待 PM 确认**

> **[督查-复盘]** 检查项目ID分配、标准子目录创建、记忆文件初始化、PM确认信号

## 阶段二：背景了解

### 步骤 2.1 — 项目背景描述

- PM 简述项目背景
- AI 倾听并记录，**不急着输出任何文档或分析**
- 仅做简单的理解确认，如：「了解了，这是一个 [一句话概括] 的项目」

**此阶段不做深度分析，只为后续梳理建立基本认知。**

### 步骤 2.2 — 项目级AI适配性快速判断 🔑

> **新增步骤**：在项目背景明确后，进行项目级的AI适配性快速判断，培养PM的AI思考意识。此阶段不做详细评估，只判断"是否值得考虑AI"。

**执行流程**：

1. **AI引导PM思考**（3个问题）：
   - "这个项目要解决的核心问题，是否有重复性、规律性的工作可以被AI替代？"
   - "当前是否有大量历史数据可以供AI学习？"
   - "如果引入AI，您更希望它提升效率（降本）还是提升效果（增效）？"

2. **快速判断**（4项勾选）：

| 判断项 | 是否满足 |
|--------|---------|
| 有大量历史数据可学 | [ ] 是 / [ ] 否 |
| 任务定义明确，专家能轻松判断对错 | [ ] 是 / [ ] 否 |
| 容忍一定程度的错误 | [ ] 是 / [ ] 否 |
| 需要规模化、7x24小时处理 | [ ] 是 / [ ] 否 |

3. **判断结论**：
- 满足≥3项 → **值得考虑AI**，进入阶段三时关注AI化机会，阶段四后做详细评估
- 满足≤2项 → **暂不考虑AI**，按常规项目流程进行

**输出**：《项目级AI适配性判断》（一句话结论，记入 `00-项目记录/context-memory.md`）

**阶段结束复核**：
- 对照行业规范，检查是否有遗漏的板块（如：用户体系、消息通知、数据统计等）
- 如有遗漏，主动询问 PM：「行业规范中通常包含 [板块名称]，这个项目需要吗？」
- 复核通过后，**等待 PM 确认进入下一阶段**

## 阶段三：需求梳理

> 此阶段核心目标：基于PM提供的功能清单，AI整理业务流程，输出待确认问题清单，PM开会确认后AI补充完善。**所有待确认问题必须在阶段三内解决，不得带入阶段四。**
>
> **关键流程**：功能清单 → AI整理流程 → 输出问题清单 → PM开会确认 → AI补充完善 → 需求细化 → **确认无遗留待确认项**

### 步骤 3.1 — 接收功能清单

- AI主动询问PM：「请提供初步的功能清单（可以是文档、文字描述或列表形式）」
- **如PM提供了功能清单**：AI接收并逐条理解
- **如PM未提供功能清单**：PM直接描述需求，AI记录并整理成功能清单
- AI复述确认：「我整理的功能清单如下，请确认是否有遗漏或理解错误」

**输出**：确认后的功能清单（写入 `00-项目记录/`）

---

### 步骤 3.2 — AI整理业务流程

- 基于**确认的功能清单** + **阶段二背景**，AI整理业务流程
- 覆盖三种路径：
  - **正向路径**：正常操作流程（主流程）
  - **取消路径**：用户中途取消/撤回的操作
  - **异常路径**：出错、超时、网络异常等处理
- 标注不确定点：
  - `[待确认]`：需要PM/客户确认的内容
  - `[AI假设]`：AI基于常识做的假设，需PM确认
  - `[行业惯例]`：按行业通用做法处理，可后续调整

**输出**：业务流程初稿（写入 `00-项目记录/`）

---

### 步骤 3.3 — 输出待确认问题清单 🔑

> **关键步骤**：AI审查业务流程，主动暴露理解中的问题，让PM带着明确的问题去和客户开会。

**AI识别以下问题类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **模糊点** | 描述不清晰，有多种理解方式 | "快速处理"是指30分钟还是2小时？ |
| **矛盾点** | 功能间逻辑冲突 | A规则说必须实名，B流程说游客可用 |
| **遗漏点** | 缺少必要环节 | 退款流程中缺少"退款失败"的处理 |
| **待决策** | 需要业务方决策的规则 | 优惠券能否叠加使用？ |
| **边界点** | 边界条件不明确 | 商品库存为0时，已加入购物车的如何处理？ |

**识别信号**（出现以下情况必须列为问题）：
1. 功能清单中出现"等"、"快速"、"视情况而定"、"原则上"等模糊词汇
2. 业务流程缺失开始/结束条件、异常处理、权限判断、数据校验
3. 两个功能对同一数据的处理规则矛盾
4. 行业规范要求但未提及（如电商未提及售后/退款）

**输出要求**：
- 严格遵循 `references/question-list-template.md` 模板
- 按优先级排序：高（阻塞流程）/ 中（影响规则）/ 低（细节优化）
- 每个问题包含：问题描述、AI当前理解、影响范围、建议确认方向
- 输出：《待确认问题清单》（写入 `00-项目记录/`）

**PM拿着问题清单与客户开会确认**

---

### 步骤 3.4 — 补充完善业务流程

- PM提供会议结论（按问题编号逐一反馈）
- AI根据会议结论补充完善业务流程

**会议结论类型处理**：

| 结论类型 | AI处理方式 |
|---------|-----------|
| **已确认** | 按确认内容更新业务流程，标记`[已确认]` |
| **待进一步确认** | 保留原问题，补充新发现的问题，输出《待确认问题清单V2》 |
| **客户也未确定** | 标注`[需PM决策]`，给出2-3个方案供PM选择 |

**循环机制**：
- 如产生新问题或高优先级问题未解决 → 回到步骤3.3，输出新版问题清单
- **循环直至无遗留待确认项（含高/中/低优先级），方可进入阶段四**
- 如PM明确要求保留某项待确认并带入后续阶段，需标注 `[PM强制保留]` 并说明原因

**输出**：完善的业务流程（写入 `00-项目记录/`）

---

### 步骤 3.5 — 需求确认与场景细化

- 基于**完善的业务流程**，AI与PM确认以下内容：
  - 项目端口（iOS / Android / Web / 小程序）
  - 系统角色（用户/管理员/商家等）
  - 核心业务场景（最典型的3-5个使用场景）
  - 关键业务规则（校验规则、约束条件、边界情况）

**对话策略**：
- 每次只聚焦一个主题，不一次性问太多
- PM描述后，AI用自己的话复述确认
- 发现矛盾或遗漏时主动追问
- 不确定的内容标注 `[待验证]`

**输出**：完整的业务流程梳理记录（写入 `00-项目记录/`）

**阶段结束复核**：
- 对照行业规范，检查流程梳理是否完整（如：是否遗漏了注册/登录、权限管理等通用流程）
- 如有遗漏，主动询问 PM 是否需要补充
- **检查待确认问题清单：确认所有问题已解决（含高/中/低优先级），无遗留待确认项**
- 复核通过后，**等待 PM 确认流程梳理完整**

> **[督查-复盘]** 检查三种路径覆盖、5种问题类型识别、PM确认信号、快速通道安全锁、**待确认问题是否全部解决**

**确认后，AI 必须主动询问**：

> 流程梳理已确认。接下来有两种模式：
> - **标准模式**：逐步对话确认功能细节、规则、逻辑 → 写PRD → 审阅 → 生成原型（阶段四~七）

> 你希望用哪种？如果要快速通道，想直接输出什么？（PRD / 原型 / 全部）

## 快速通道模式

> 步骤 3.5 结束后可选。AI 根据行业规范自动补齐细节，跳过阶段四的逐模块对话，直接输出目标文件。
>
> **注意**：若步骤 3.3 输出的问题清单中有高优先级问题未解决，**禁止进入快速通道**，必须先完成问题确认。

### 触发方式

PM 在步骤 3.5 结束后明确选择：
- 「快速通道，直接出PRD」
- 「快速通道，直接出原型」
- 「快速通道，全部输出」
- 「一键生成」

### 自动补齐原则

AI 根据以下规则自动填充未确认的细节：

| 维度 | 填入规则 |
|------|---------|
| 功能模块 | 按行业标准模块清单补齐（详见 `references/industry-rules.md` 对应行业章节） |
| 业务规则 | 按行业通用惯例（如：电商→30分钟未支付自动取消） |
| 数据逻辑 | 按常识推导（如：支付后生成订单号，格式 YYYYMMDD+随机数） |
| 权限控制 | 按角色默认权限（如：普通用户只能看自己的订单） |
| 异常处理 | 按行业标准处理（如：网络异常→提示重试，超时→自动回滚） |
| 页面框架 | 按行业标准布局模板 + 数据类型匹配排版模式 |
| 交互链路 | 按页面层级默认跳转关系 |

### 标注规则

自动补齐的内容使用以下标注：
- `[AI补齐-行业惯例]`：基于行业普遍做法的决策
- `[AI补齐-常识推导]`：基于因果逻辑的推导
- `[AI补齐-默认值]`：选择了行业最常用方案

### 执行流程

#### 快速通道 → 直出 PRD

1. 加载行业自动补齐规则
2. AI 自动完成功能模块拆分 + 规则填充（内部执行，不对话）
3. 输出「自动补齐方案摘要」供 PM 快速审阅（模块清单+关键规则+待确认项）
4. PM 确认或提出修改 → 修改后输出最终 PRD

#### 快速通道 → 直出原型

1. 加载行业自动补齐规则
2. AI 自动完成：模块拆分 → 规则填充 → 页面框架设计（内部执行，不对话）
3. 输出「自动补齐方案摘要」+ 「页面框架设计」供 PM 快速审阅
4. PM 确认后，直接生成 HTML 原型（跳过逐级确认，但保留逐级闭环生成）
5. 生成后执行全量自检清单 + 交付

#### 快速通道 → 全部输出

1-3 同上
4. 先输出 PRD
5. 再生成 HTML 原型
6. 两次输出均需 PM 审阅确认

### 快速通道的边界

**以下情况 AI 必须暂停并询问 PM（不能自动补齐）**：
- 行业规范中存在 2+ 种同样常见的做法，无法确定选哪个
- PM 在阶段一~三（含问题清单确认过程）中明确表达过特殊偏好
- 涉及合规/法律风险的决策（如金融产品条款、隐私授权范围）
- 项目核心差异化功能（非行业通用功能）
- 阶段三/四有遗留待确认项未解决（含PM强制保留项）

**以下情况直接采用行业最常见方案，不询问**：
- 支付超时时间、退款流程、评价机制等运营规则
- 列表排序规则、搜索逻辑、分页数量等交互细节
- 通知推送时机、消息提醒方式等触达策略
- 页面框架布局、组件排列方式等 UI 结构

### 快速通道质量保障

快速通道产出物必须通过和标准模式同等严格的自检清单：
- PRD：五部分结构 + 自检5项 + 质检5项
- 原型：全链路校验 + HTML自检清单 + 交付标准全部检查项
- 不合格 → 自动修复后再提交 PM

### 步骤 4.1 — 功能模块整理

- 基于已确认的业务流程，整理功能板块
- 通过**反复对话**确认每个模块的细节：
  - 业务规则（校验规则、约束条件、边界情况）

  - 权限控制（谁可以操作、权限边界）
  - 关联关系（模块间的依赖和交互）
  - 异常处理（出错时的应对策略）

**对话策略**：
- 逐模块确认，不跳过
- 不确定时给出 2-3 个方案（含优缺点和推荐度）
- 标注 [待PM确认] 和 [MVP]
- **如PM暂时无法确认某项，必须追问并获得PM明确答复（确认/否决/强制保留）后方可继续**

**输出**：功能模块清单 + 优先级 + 详细规则（写入 `00-项目记录/`）

**阶段结束复核**：
- 对照行业规范，检查功能模块是否有遗漏（如：设置、帮助中心、关于我们等通用模块）
- 如有遗漏，主动询问 PM 是否需要补充
- 检查每个模块的规则是否符合行业标准和合规要求
- **检查是否有遗留待确认项：所有标注 [待PM确认] 的内容必须已解决（确认/否决/PM强制保留），方可进入阶段五**
- 复核通过后，**等待 PM 确认所有功能模块细节**

### 步骤 4.2 — AI功能单元拆解与详细评估 🔑

> **新增步骤**：功能模块确认后，对涉及AI的功能进行单元级详细评估。此时业务流程已清晰，拆解更准确。

**前置条件**：阶段二判断为"值得考虑AI"的项目才执行此步骤。若阶段二判断为"暂不考虑AI"，跳过此步骤。

**执行流程**：

#### 第一步：拆解AI功能单元

基于已确认的功能模块，AI引导PM拆解AI功能单元。

**引导问题**：
- "在已确认的功能模块中，哪些环节可以被AI替代或增强？"
- "每个AI环节是否有明确的输入数据和期望输出？"
- "请把AI相关功能拆成几个'最小AI功能单元'"

**拆解原则**：
- 每个单元对应一个完整的"输入→处理→输出"闭环
- 单元之间尽量独立，减少耦合
- 颗粒度适中：既不过大（难以评估），也不过小（价值不明显）

**拆解示例**：
- 智能客服系统 → 单元1：意图识别 / 单元2：回复生成 / 单元3：情绪识别
- 商品推荐系统 → 单元1：用户画像 / 单元2：推荐排序

**输出**：AI功能单元清单

#### 第二步：逐单元详细评估

对每个AI功能单元，AI填写《AI化可能性评估》，严格遵循 `references/ai-assessment-template.md` 模板。

**7个评估维度**：
1. 问题定义与AI适配性判断（4项勾选）
2. AI任务类型判断（分类/回归/聚类/生成/排序）
3. 数据可行性快速自查
4. 核心技术指标优先级定义
5. 失败场景与容错成本预估
6. 价值与成本粗略估算
7. 综合评估结论

**多单元汇总**：

| 序号 | AI功能单元 | 适配性 | 综合建议 | 优先级 |
|------|-----------|--------|---------|--------|
| 1 | | | | |

**项目级AI策略**：
- **全部建议尝试**：项目整体适合AI化，按优先级逐个实施
- **部分建议尝试**：优先实施高适配性单元，低适配性单元寻找替代方案
- **全部不建议**：项目暂不适合AI化，按常规项目流程进行

**输出**：
- 每个功能单元独立评估
- 多单元汇总评估表
- 保存到 `00-项目记录/ai-assessment/`

**评估后处理**：
- 高适配性单元：在PRD中明确AI功能需求
- 低适配性单元：在PRD中标注为常规功能或[MVP]

## 阶段六：原型生成

> **原型输出格式**：
> - **单端口项目**：输出为单个 HTML 文件，所有样式、交互逻辑内嵌，不依赖外部资源
> - **多端口项目**：按端口拆分为独立 HTML 文件（每端口一个文件），避免单文件过大导致维护困难和加载缓慢
>
> **此阶段核心机制 — 设计师（资深UE设计师Agent）三层审查**：
> 1. **设计纲要阶段**：设计师主导生成设计纲要，设计分析师审查，设计师判定并调整
> 2. **框架设计阶段**：设计师审查框架，设计分析师审查，设计师判定并调整
> 3. **交付前阶段**：设计师走查 + 验收员用户视角测试，设计师判定并输出修复方案
>
> **此阶段规则加载优先级（从高到低）**：
> 1. `references/frontend-design-rules.md`（案例驱动规则，从实际页面提炼，最高优先级）
> 2. `references/prototype-rules.md`（全行业通用规范）
> 3. `references/user-centric-design.md`（用户群体差异化设计指南，多端口设计分化参考）
> 4. `references/industry-rules.md`（行业特定规范）
> 5. `references/industry-templates.md`（行业模板库）
> 6. `references/component-library.md`（组件库）
> 7. `references/design-patterns.md`（设计模式库）
>
> **冲突处理**：案例规则与通用规范冲突时，以案例规则为准（但需标注冲突供后续审核）。
>
> **此阶段必须严格遵循 `references/prototype-rules.md` 中以下关键规范**：
> - 功能拆分与合并判断原则（公共/隐私分离、主次分明）
> - 导航架构设计原则（用户视角，非系统模块直译）
> - 统一设计 Token（间距/字体/图标/圆角/颜色）
> - 视口与容器约束（phone-frame 自适应视口，z-index 层级规范，强制声明规则）
> - 页面布局设计原则（视觉层次、分区、图文结合）
> - 数据展示排版规范（5种列表模式 + 选择决策树 + 各类型信息规范）
> - HTML 产出物自检清单（5项强制检查）
> - 浏览器兼容性（SVG currentColor、Flex min-height:0）
> - Z-Index 强制声明 + 排查清单

> **[督查-预防]** 检查PRD是否已确认、阶段六规则文件（11个）是否全部加载

> **调用方式**：`references/designer.md` — 设计师Agent

> 设计纲要是规则的"项目化实例"，把通用规则应用到具体项目。设计师基于其设计经验，在PRD基础上主动补充隐含功能、优化交互方案、提升设计质量，确保AI在写代码前先把设计想清楚。

#### 6.4.1 设计师设计纲要生成流程

**第一步：设计师读取输入**
- PRD文档（阶段五产出）
- 行业类型（从阶段二/三确定）
- 端口信息（iOS/Android/Web/小程序）
- 目标用户画像

**第二步：设计师主导生成（8章节）**

设计师严格遵循 `references/design-outline-template.md` 模板，基于其专业能力生成：

1. **产品设计基调** — 设计师给出设计关键词、目标、风格参照、遵守的规则编号
2. **布局架构** — 设计师设计导航体系、关键页面布局，每页标注规则编号和决策依据
3. **交互设计** — 设计师定义容器选择标准、核心交互流程、加载与刷新，每场景标注规则编号
4. **视觉规范** — 设计师制定色彩系统、字体体系、间距系统、组件样式（具体到数值）
5. **状态覆盖计划** — 设计师规划全局状态矩阵、关键空状态设计
6. **一致性自查** — 设计师检查组件/交互/文案/命名一致性
7. **AI补充项清单** — 设计师主动补充的设计细节（隐含功能、优化建议），全部标注"待确认"
8. **待确认项** — 设计师提出PM需要决策的问题，给出方案A/B和推荐

**设计师补充原则**：
- 每个页面至少补充2-3个PRD未提及的隐含功能
- 每个交互场景至少覆盖5种交互组件
- 每个设计决策必须有用户场景或业务目标支撑
- 所有补充项标注"待确认"，不替PM做决定

#### 6.4.2 设计师自检设计纲要

设计师生成后必须自检（7项）：
- [ ] 每个页面有明确的定位和布局参照（参照哪个APP的哪个页面）
- [ ] 每个设计决策标注了"遵守的规则编号"和"决策依据"
- [ ] 每个页面有视觉层次（三层内容：强调/主体/辅助）
- [ ] 每个页面有隐含功能（至少补充2-3个PRD未提及的功能）
- [ ] 交互组件覆盖完整（至少包含5种交互组件）
- [ ] AI补充项全部标注"待确认"
- [ ] 设计决策有原因（每个决策都有用户场景或业务目标支撑）

自检不通过，设计师自动修正后重新自检。

设计师以"审查者"身份对设计纲要进行最终审查：

**审查维度**：
1. **布局合理性** — 页面布局是否符合行业惯例，信息层次是否清晰

3. **视觉一致性** — 色彩/字体/间距是否统一，是否符合设计基调
4. **补充价值** — AI补充项是否有价值，是否过度设计

| 1 | xxx | 高/中/低 | xxx |

### 亮点清单
- [亮点1]
- [亮点2]

[如审查不通过，输出修正后的设计纲要]

### 【第二层】步骤 6.6 — 逐级闭环生成 + 交互补全

按页面层级逐级生成，**每级生成后必须形成完整交互闭环**。

#### 6.6.1 生成优先级

**第一级：入口页面**
- 登录/注册页（如需要）
- 启动页/引导页（如需要）
- **闭环要求**：登录成功后能跳转到主导航页

**第二级：主导航页面**
- 底部导航各 TAB 主页面
- **闭环要求**：各 TAB 之间可以正确切换，每个 TAB 页的入口链接可点击

**第三级：二级页面**
- 从主导航进入的各二级页面
- **闭环要求**：从主导航可以正确跳转到二级页，二级页有返回按钮

**第四级：三级页面**
- 从二级页面进入的更深层页面
- **闭环要求**：返回路径完整，交互有效

每级内按 P0 → P1 → P2 → P3 顺序生成。

#### 6.6.2 交互补全机制（强制）

**每个页面生成时，必须对照"交互补全清单"逐项检查，缺失的必须补充。**

详见 `references/prototype-rules.md` 交互补全清单章节，包含14项必检交互：
- 页面跳转、返回路径、中部弹窗、底部弹窗、ActionSheet、Toast反馈
- 加载状态、空状态、错误状态、下拉刷新、上拉加载、左滑操作
- 搜索功能、筛选排序

**交互补全原则**：设计纲要中规划的交互组件必须实现，未规划的交互组件如发现缺失也必须补充。

#### 6.6.3 每级生成后自检

**HTML 产出物自检清单**（8项）：
1. 脚本完整性（JS 在 `<script>` 内）
2. 无重复块
3. 核心函数唯一
4. DOM 完整性
5. Design Token 合规（图标/图片/间距/字体尺寸）
6. SVG 与文字容器规范
7. 滚动条隐藏
8. 实机预览验证（浏览器打开确认无白屏/乱码/报错/布局失调）

**自动截图检查**：
1. 启动本地HTTP服务器预览原型
2. 使用浏览器工具截取各页面截图
3. 对照检查清单逐项核对截图：
   - 布局比例是否协调（图标/图片/文字大小）
   - 是否与行业参照APP布局模式一致
   - 有无明显视觉异常（元素重叠/错位/溢出）
4. 发现问题立即修复，不交付PM预览

#### 6.6.4 验收员测试（可选） 🔑

> **新增步骤**：每级页面生成并通过自检后，可调用验收员Agent进行用户视角测试。
>
> **调用方式**：`references/inspector.md` — 验收员Agent
>
> **触发条件**：
> - 第一级和第二级页面生成后（建议调用）
> - 全部页面生成后（必须调用）
> - PM要求测试时

**验收员测试流程**：
1. 验收员阅读项目上下文（PRD、设计纲要、框架设计）
2. 验收员以用户视角测试原型（7个维度：导航/布局/交互/状态/内容/边界/代码）
3. 输出测试报告（🔴高/🟡中/🟢低优先级）
4. 报告提交给设计师

**设计师处理流程**：
1. 设计师收到验收员测试报告
2. **逐条判定**：按"项目标注>规范铁律>行业准则>大众选择"标准判定每条反馈的合理性
   - 验收员标注"待确认"或"项目特色"的 → 查阅PRD/设计纲要后判定，不确定询问PM
   - 验收员建议"改成XX"但与项目风格冲突的 → 标注"与项目风格不符，忽略"
3. 仅对判定为合理的问题，输出修改方案，交给AI执行
4. 高优先级问题必须修复
5. 修复后验收员可重新测试验证

**测试维度**（详见 `references/inspector.md`）：
- 导航测试 — 用户会不会迷路？
- 布局测试 — 页面是否美观、信息层次是否清晰？
- 交互测试 — 操作是否有反馈？交互是否自然？
- 状态测试 — 各种状态下页面是否正常？
- 内容测试 — 文案是否"说人话"？
- 边界测试 — 极端情况下是否正常？
- 代码审查 — 代码层面的样式/布局/结构是否符合规范？（静态分析发现视觉和交互隐患）

**测试输出**：
```
## 验收员最终测试报告

### 测试概述
- 测试范围：全量测试
- 发现问题总数：[X个高/Y个中/Z个低]

### 问题清单
🔴 【高】[页面] — [问题]
   - 影响：...
   - 依据：...
   - 建议：...

🟡 【中】[页面] — [问题]
   - 影响：...
   - 建议：...

🟢 【低】[页面] — [问题]
   - 建议：...

### 亮点清单
- [亮点1]
```

#### 6.10.3 设计师综合判定与修复

设计师收到两份报告（自己的走查报告 + 验收员测试报告）后：

1. **汇总问题**：将两份报告的问题合并，去重
2. **逐条判定**：
   - 两份报告都提到的问题 → 高优先级，必须修复
   - 设计师走查发现但验收员未发现 → 中优先级
   - 验收员发现但设计师未发现 → 需要特别重视（用户视角独特发现）
   - **验收员标注"待确认"或"项目特色"的 → 设计师查阅PRD/设计纲要后判定，不盲目采纳**
   - **验收员建议"改成XX"但与项目风格冲突的 → 标注"与项目风格不符，忽略"**
3. **输出修复方案**：仅对判定为合理的问题，按"判定合理性 → 输出修改方案 → 交给AI执行"流程处理
4. **修复后验证**：修复完成后，设计师和验收员分别验证

修复全部通过后，进入全链路校验。

> **[督查-复盘]** 检查设计师走查5维度、验收员最终测试7维度调用、设计师综合判定、修复方案输出

## GitHub推送流程（独立触发）

> 推送操作与技能更新解耦，可在任意时间独立执行。

- PM说"推送GitHub"

- PM说"提交代码"

### 执行流程

1. **检查Git状态**
   - `git status` 查看变更文件
   - 确认变更符合预期

2. **执行推送**
   ```bash
   git add -A
   git commit -m "[更新说明]"
   git push
   ```

3. **确认推送结果**
   - 检查push输出是否成功
   - 如失败，分析原因（网络/权限/冲突）并报告PM

4. **输出推送报告**
   ```markdown
   ## GitHub推送报告
   - 推送时间：[日期时间]
   - 变更文件数：X个
   - Commit信息：[内容]
   - 推送结果：成功 / 失败（原因）
   ```

### 注意事项

- 推送前无需PM再次确认更新内容（已在步骤7.3/7.4中确认过）
- 如推送失败，不自动重试，报告PM由PM决定
- GitHub路径保持原路径不变

## 版本回溯机制

### 版本记录文件

每个项目维护一个 `00-项目记录/version-log.md`，结构如下：

```markdown
# 版本记录

## v1.0 - [日期时间]
- 阶段: 需求梳理
- 变更: 初始版本
- 文件: 00-项目记录/流程梳理-v1.0.md

## v1.1 - [日期时间]
- 阶段: 需求梳理
- 变更: 补充异常路径
- 文件: 00-项目记录/流程梳理-v1.1.md

## v2.0 - [日期时间]
- 阶段: PRD
- 变更: 初始PRD
- 文件: 01-需求文档/PRD-v2.0.md
```

### 版本保存规则

1. **每个阶段产出物保存为独立文件**，文件名包含版本号
2. **每次重大修改后**，创建新版本，旧版本保留
3. **版本号规则**：
   - 主版本号（v1.0, v2.0）：阶段切换时递增
   - 次版本号（v1.1, v1.2）：同一阶段内重大修改时递增

### 回溯操作

当 PM 说「回溯到 [版本号]」或「回到之前的版本」时：

1. AI 读取版本记录文件，找到对应版本
2. 加载该版本的产出物
3. 从该版本继续工作
4. 新版本号接续（如从 v2.0 回溯到 v1.2，新版本为 v1.3）

### 回溯触发场景

- PM 对当前产出不满意，希望回到之前某个状态
- 发现当前方向偏离了已确认的需求
- 需要对比不同版本的差异

---

## 确认信号

以下信号视为 PM 确认，可进入下一步：
- 「确认」
- 「可以」
- 「没问题」
- 「继续」
- 「下一步」

PM 未确认前不得推进。

## 多方案决策

不确定时给出 2-3 个方案（含优缺点和推荐度），等 PM 选择。
PM 未选择前不得推进。
PM 也不确定时：选行业最常用方案 + 选实现成本最低方案 + 以 MVP 为第一优先级，标注 [MVP]。

## 行业规范

不确定时主动反问，PM 也不确定时选最常用方案标注 [MVP]：

| 行业 | 必要模块/规范 |
|------|-------------|
| 电商 | 交易履约、售后责任、优惠叠加、物流追踪、评价体系 |
| 内容社区 | UGC 审核、推荐伦理、举报机制、内容分级 |
| 企业服务 | 多租户隔离、RBAC 权限、操作审计、数据备份 |
| 金融 | PCI DSS、资金流一致性、风控规则、合规披露 |
| 教育 | 课程体系、学习进度、证书发放、互动答疑 |
| 医疗健康 | 数据隐私（HIPAA等）、处方合规、问诊流程 |
| 社交 | 好友体系、消息推送、隐私设置、举报封禁 |
| O2O/本地生活 | 商家入驻、服务履约、评价退款、定位服务 |

**行业规范反问机制**：
- 每个阶段结束时，对照上表检查当前项目是否有遗漏的必要模块
- 发现遗漏时主动询问：「[行业] 项目通常需要包含 [模块]，当前方案中未涉及，这个项目需要吗？」
- PM 确认不需要则标注 [已排除]，确认需要则补充到方案中
